# 워크벤치 (cozy-workbench)

앱을 dev로 실행하면 `/cozy/dev/workbench`에서 앱의 개요를 보고, 화면의 구조, 상태별 미리보기, 소스를 본다. 결정은 [ADR-0036](../adr/0036-workbench.md)과 [ADR-0038](../adr/0038-workbench-redesign.md)(용어, 디자인 개선)에 있다. 워크벤치는 dev 전용 도구이고 배포 패키지에는 들어가지 않는다.

- **지금 되는 것**: 개요(화면, 모듈, 규칙 위반, 미구현 항목), 머리의 검색(화면, 화면 안의 동작, 화면 이벤트, 컴포넌트, 생성 항목, 모듈), 모듈별 화면 목록, 여러 상태를 창에서 나란히 보기(상태 비교), 화면의 구조 트리(패턴 → 영역 → 프래그먼트, 접고 펴기), 선택한 항목의 속성과 문자열 매개변수 수정(변경 파일 확인 → 적용), 요소마다 붙은 화면 안의 동작과 htmx 요청 보기와 붙이고 떼기(`cozy attach`. 이름은 선택 칸), 미리보기에서 고른 요소에 붙이기(컴포넌트가 없는 요소는 컴포넌트를 골라 자리로, `data-*` 칸), 상태와 화면 너비 전환, 좌우 칸 접기, 템플릿(화면이 넣는 앱 템플릿 포함), 화면 명세, 동작 명세, 만든 JS의 소스 보기, 요소를 눌러 소스 위치 찾기, 에이전트용 글 복사, 검사 결과와 수정 명령, 모듈 의존성 다이어그램과 표, 모듈의 화면 안의 동작과 화면 이벤트, 폼으로 cozy 명령 실행(입력 항목은 속성 표와 그리드, 앱의 값은 선택 칸, 변경 파일은 모듈·계층별 트리, 확인 → 적용), 동작 고치기(지금 항목으로 채운 폼, 이름 바꾸기, 지우기, 낱말 표와 칸의 제안), 샘플 데이터 수정(객체는 속성 표, 목록은 그리드, 타입에 맞는 입력)과 상태 복제
- **하지 않는 것**: 자유 배치, 색·간격 편집, HTML 편집(속성 패널은 fragment 호출의 문자열 인자만 고친다), 스펙에 키를 더하고 빼기

## 용어

워크벤치 화면은 아래 용어를 쓴다. 한 개념에 용어 하나다. `WorkbenchTermsTest`가 메뉴, 상태 이름, 구조 트리, 생성 항목 목록을 확인한다.

- **표기**: 사람이 읽는 이름을 앞에, 식별자를 뒤에 고정폭 회색 글자로 쓴다(`페이지네이션 pagination`). 식별자는 지우지 않는다.
- **낱말**: 동작은 일반 UI 용어(추가, 삭제, 저장, 적용, 확인, 검색, 복사)를, 개발 용어는 통용 표기(프래그먼트, 컴포넌트, DTO, 이벤트 리스너)를 쓴다. 새 조어를 만들지 않는다.
- **에이전트용 글**은 식별자로 쓴다(`Inside: list-with-filter (패턴) > …`).
- **cozy 명령의 메시지**(레시피 설명, 고치는 법, 다음 할 일)는 명령이 낸 그대로 보인다. 이 용어집의 대상이 아니다.

| 개요 | 워크벤치의 첫 화면. 화면, 모듈, 규칙 위반, 미구현 항목을 한 번에 본다 (메뉴) | |

| 동작 고치기 | 화면 동작 폼을 컴포넌트의 지금 항목으로 채워 고치는 일. 바꾼 행은 `cozy add behavior`, 지운 행은 `cozy remove behavior`의 한 계획 | |
| 낱말 표 | 동작 명세에 쓰는 상태의 종류, 계산 함수, 동작 단계, 이벤트 값의 모양과 설명(`cozy recipes --json`의 `vocabulary`) | |
| 화면 이벤트 | 창으로 오가는 이벤트 `모듈:이름`. 동작 명세의 `emit`·`listens`, 서버의 `HX-Trigger`, `hx-trigger`가 내고 받는다. 앱 이벤트(`CozyEvent`)와 다르다 | |

- **상태 이름**: 관례 이름은 표시 이름으로 보이고 식별자는 버튼의 `title`에 남는다. 그 밖의 이름은 식별자 그대로다.

  | 식별자 | 표시 이름 |
  | --- | --- |
  | `default` | 기본 |
  | `empty` | 데이터 없음 |
  | `noResults` | 검색 결과 없음 |
  | `paged` | 여러 페이지 |
  | `invalid` | 입력 오류 |

- **컴포넌트 이름**: 매니페스트의 `label`이다([ui.md](ui.md)). 프레임워크 항목은 KRDS에 같은 역할의 컴포넌트나 기본 패턴이 있으면 그 명칭을 쓴다. `label`이 없으면 종류(컴포넌트, 프래그먼트, 영역)와 식별자로 표시된다.
- **생성 항목 이름**: `cozy recipes --json`의 `title`과 `group`이다([cli.md](cli.md)).
- **규칙 이름**: 검사 화면은 규칙 ID 앞에 이름을 붙인다(`다른 모듈 템플릿 참조` `오류 R3`). 이름은 `cozy-rules`의 `RuleNames`에 있다.
- **워드마크**: 머리의 "Cozy Workbench"는 Courgette(SIL OFL 1.1)의 글자를 SVG 경로로 바꾼 것이다. 글꼴 파일은 없다. 글자색(`currentColor`)을 따른다.

## 넣기

- 새 앱: 아키타입이 `pom.xml`에 `cozy-workbench`를 넣는다.
- 이미 있는 앱: `cozy enable workbench`. `cozy-ui` 블록 바로 뒤에 넣는다. cozy-parent가 1.2.0보다 낮으면 실패한다.

```xml
<dependency>
  <groupId>io.salvia95.cozy</groupId>
  <artifactId>cozy-workbench</artifactId>
</dependency>
```

- 앱 코드는 이 모듈의 타입을 쓰지 않는다. 자동 설정만 쓴다.
- **배포 패키지**: `cozy-parent`가 실행 jar에서 `cozy-workbench`, `cozy-cli`, `cozy-rules`를 뺀다. 제3자 라이선스 목록에도 없다.

## 켜지는 조건

| 속성 | 기본값 | 뜻 |
| --- | --- | --- |
| `cozy.dev.workbench.enabled` | dev 프로필이면 `true`, 아니면 `false` | `/cozy/dev/workbench` 등록 |
| `cozy.dev.workbench.project-dir` | 없음 | 앱 프로젝트 폴더를 직접 정한다. 위로 올라가며 찾지 않고 이 폴더만 본다 |
| `cozy.dev.workbench.live-resources` | `true` | 앱의 템플릿과 `static/`을 소스 폴더에서 먼저 읽는다(바로 보기). `false`면 빌드 결과만 읽는다 |

- 패턴 카탈로그(`cozy.dev.catalog.enabled`)가 켜져 있어야 한다. 매니페스트와 화면 미리보기(`/cozy/dev/catalog/screen`)를 카탈로그가 준다.
- **앱 프로젝트 폴더에서 실행해야 구조와 소스가 보인다.** 실행한 폴더에서 위로 올라가며 `pom.xml`과 `src/main/java`가 있는 폴더를 찾는다. 못 찾으면(jar나 app-image로 실행) 미리보기만 보이고 화면이 이유를 알린다.
- dev 실행에는 JDK가 필요하다(cozy-cli가 javac 파서를 쓴다).
- **바로 보기**: 워크벤치가 켜지고 앱 프로젝트 폴더를 찾으면, 실행 중인 앱이 앱의 템플릿과 정적 자원을 소스 폴더에서 먼저 읽는다. 워크벤치로 적용한 템플릿, 동작 명세에서 만든 JS, 정적 파일이 다시 빌드하지 않고 새로고침만으로 미리보기와 앱 화면에 보인다.
  - 템플릿: `src/main/resources/templates/`를 먼저 보는 템플릿 해석기(`SourceTemplateResolver`, 캐시하지 않는다). 소스에 없는 템플릿(프레임워크 템플릿 `cozy/…`)은 빌드 결과에서 읽는다. 미리보기의 소스 위치(`data-cozy-src`)도 소스의 줄이다.
  - 정적 자원: `spring.web.resources.static-locations`의 맨 앞에 `src/main/resources/static/`을 둔다. 앱 모듈의 컴포넌트 묶음(`/cozy/modules.js`)도 같은 곳을 먼저 읽는다(`cozy.ui.module-script-folders`, [ui.md](ui.md)). 앱이 이 속성을 정했으면 그 값이 이긴다.
  - Java, SQL, 설정은 지금처럼 다시 빌드하고 실행해야 한다. 확인 화면이 파일마다 알린다.
  - 배포 패키지와 dev 프로필이 아닌 테스트(렌더링 검사)는 워크벤치가 없으므로 빌드 결과만 읽는다. 끄려면 `cozy.dev.workbench.live-resources=false`다.

## 주소

고른 것은 모두 주소의 파라미터에 있다. 주소를 그대로 주고받을 수 있다.

| 파라미터 | 값 | 기본 |
| --- | --- | --- |
| `spec` | 화면 스펙 이름 (`memo-list`) | 없으면 개요 |
| `state` | 스펙의 상태 이름 | 스펙의 첫 상태 |
| `w` | 미리보기 폭: `full`, `1024`, `768`, `390` | `full` |
| `view` | `preview`, `template`, `spec`(화면 명세), `behavior`(동작 명세), `script`(만든 JS)는 가운데 칸에 보일 것. `fixture`는 미리보기 옆 오른쪽 칸에 샘플 데이터 | `preview` |
| `template` | `view=template`에서 볼 템플릿(`memo/internal/fields`). 화면 템플릿이나 화면이 넣는 앱 템플릿(구조 트리의 대상, 동작이 붙은 요소의 템플릿)이어야 한다. 아니면 404 | 화면 템플릿 |
| `module` | `view=behavior`, `script`에서 볼 모듈. 화면이 쓰는 앱 컴포넌트의 모듈이어야 한다. 아니면 404 | 그 가운데 첫 모듈 |
| `compare` | `true`면 상태 비교 창을 연 채로 시작한다(개요의 "상태 비교") | `false` |
| `node` | 다시 고를 구조의 줄 번호(매개변수 수정과 붙이기 뒤에 붙는다) | 없음 |
| `at` | 요소에 붙이기 카드를 열 요소: 앱 템플릿:줄(`memo/internal/fields:9`). 모양이 아니면 400, 없는 템플릿이면 404 | 없음 |
| `component` | `at`에서 고른 컴포넌트(컴포넌트가 없는 요소) | 없음 |

- `spec`이 없으면 개요가 보이고 나머지 파라미터는 쓰지 않는다. 메뉴의 "화면"(`/cozy/dev/workbench/screens`)은 첫 화면(`?spec={첫 화면}`)으로 넘긴다. 화면이 없으면 빈 화면 보기다.
- 없는 `spec`이나 `state`는 404, 목록에 없는 `w`나 `view`는 400이다.
- 화면 목록, 상태, 화면 너비를 바꿔도 `view=fixture`는 이어진다.
- 소스 보기(`view=template`, `view=spec`)의 줄마다 `id="L{줄}"`이 있다.

## 화면 보기의 구성

화면 보기(`/cozy/dev/workbench?spec=…`)는 세 칸이다. 세 칸이 화면 높이를 채우고 칸마다 따로 스크롤한다. 1200px보다 좁으면 한 열로 쌓인다([design.md](design.md) §2).

| 칸 | 내용 |
| --- | --- |
| 왼쪽 | 화면 목록(모듈별로 묶고, 화면 명세의 `title`과 식별자로 보인다. `title`이 없으면 식별자만)과 선택한 화면의 구조 트리 |
| 가운데 | 탭 `미리보기 · 템플릿 · 화면 명세`, 화면이 앱 컴포넌트를 쓰면 `· 동작 명세 · 만든 JS`. 미리보기에는 상태(하나만 고른다), 상태 비교, 화면 너비, 요소 선택 스위치가 있다. 소스는 줄 번호가 있고 `#L7`로 그 줄에 간다. 템플릿 탭은 화면이 넣는 앱 템플릿이 둘 이상이면 그 목록을, 동작 탭은 모듈이 둘 이상이면 모듈 목록을 위에 보인다. 동작 명세와 만든 JS 위에는 고치는 길(`cozy add behavior`, `cozy sync behaviors`, 만든 JS는 손으로 고치지 않음)을 한 줄로 알린다 |
| 오른쪽 | 탭 `속성 · 샘플 데이터`. 샘플 데이터를 고치는 동안 미리보기가 가운데에 그대로 보인다 |

- **머리**: 워드마크, 메뉴, 검색 칸이 한 줄이다. 모든 워크벤치 화면이 같은 머리를 쓴다. 워드마크는 개요로 간다.
- **상태**: 미리보기는 상태 하나를 그린다. 상태 버튼은 하나만 고른다.
- **상태 비교**: 상태가 둘 이상이면 상태 버튼 옆의 "상태 비교"가 창(Tabler 모달)을 연다.
  - 창 위에서 비교할 상태를 체크박스로 고른다. 한 번에 4개까지다. 4개를 고르면 나머지 체크박스는 꺼지고 이유가 보인다. 처음에는 지금 상태와 그 뒤의 상태들이 4개까지 골라져 있다.
  - 고른 상태만 카드로 놓는다. 768px 이상은 두 열(4개면 위 2개, 아래 2개), 좁으면 한 열이다. 창 크기는 고른 수와 관계없이 화면 높이에 맞춰 같고, 넘치면 창 안에서 스크롤한다. 미리보기는 창이 열린 뒤 고른 카드만 불러온다. 상태가 많아도 한 번에 4개만 그린다.
  - 창 안의 화면 너비(`전체 · 1024 · 768 · 390`)로 미리보기를 그릴 폭을 바꾼다(`full`은 1280×800, `1024`는 1024×768, `768`은 768×1024, `390`은 390×844). 카드 폭에 맞게 줄이는 비율은 `workbenchThumb`이 정한다. 주소에는 남지 않는다.
  - 카드를 누르면 그 상태의 미리보기로 간다. 지금 상태의 카드는 테두리가 파랗고 "지금 보는 상태"가 붙는다. 미리보기 안은 누르거나 키보드로 들어갈 수 없다(`inert`).
- **칸 접기**: 가운데 칸 머리의 버튼 두 개로 왼쪽 칸과 오른쪽 칸을 접는다. 둘 다 접으면 미리보기가 전체 너비를 쓴다. 접은 상태는 브라우저에 남아(`cozyDisclosure`, `localStorage`의 `cozy.workbench.panes`에 접은 칸 이름의 목록) 화면을 옮겨도 유지된다. 주소에는 넣지 않는다.
- **속성**: 왼쪽 열이 항목 이름인 표다. 아무것도 선택하지 않으면 화면의 속성(이름, 식별자, 모듈, 템플릿, 화면 명세, 상태, 규칙 위반)이 보인다. 구조의 줄이나 미리보기의 요소를 선택하면 그 항목의 속성으로 바뀐다.

  | 구획 | 항목 |
  | --- | --- |
  | 기본 정보 | 이름, 종류, 식별자(매니페스트의 id), 설명(매니페스트의 `purpose`), 상위 경로, 소스 위치(`파일:시작–끝`), 템플릿(삽입한 템플릿) |
  | 매개변수 | 삽입에 넘긴 인자. 이름은 매니페스트 파라미터의 `label`(없으면 파라미터 이름), 값은 템플릿에 적힌 그대로다 |

  - 다른 템플릿이 그린 요소를 선택하면 "렌더링한 템플릿" 행이 붙는다.
  - **매개변수 수정**: 글자 그대로의 문자열 인자(`'고정'`)는 입력 칸으로 보인다. 매니페스트가 값을 정했으면(`choices`) 선택 칸이다(`중립 (neutral)`). 지금 값이 정한 값 밖이면 "(정한 값 밖)"으로 맨 앞에 남는다. 표현식과 선택자는 글자 그대로 보이고 고치지 않는다.
    - **변경 파일 확인**을 누르면(`POST /cozy/dev/workbench/arg`) `cozy set arg … --dry-run`의 결과가 오른쪽 칸 위에 보인다(바꿀 파일, `badge(…) 2번째 인자 tone: 'neutral' → 'info'`, 명령과 복사). **적용**을 누르면 같은 명령을 실행한다. 거절하면 이유를 보이고 파일은 바뀌지 않는다([cli.md](cli.md)의 set arg).
    - 고친 뒤에는 주소에 `node={줄}`이 붙어 같은 줄이 다시 선택된다.
    - 적용하면 구조 트리와 속성은 바로 바뀐다(소스를 읽는다). 미리보기도 새로고침하면 바뀐다(아래 "바로 보기"). 끄면 다시 빌드하고 실행한 뒤 바뀐다.
    - 쓰는 요청의 조건은 "코드 생성"과 같다(CSRF, 같은 Origin, 프로젝트 폴더, `step`이 `plan`이나 `apply`). 없는 화면이면 404다.
  - **화면 안의 동작**: 줄에 보이는 요소 가운데 Alpine 속성이나 htmx 속성이 붙은 것이 있으면 구조 트리의 그 줄에 번개 아이콘과 `동작 N`(요소 수. 마우스를 올리면 "화면 안의 동작이 붙은 요소 N개")이 식별자 뒤에 붙고(칸이 좁으면 다음 줄로 내려간다), 속성 표에 "화면 안의 동작 N" 구획이 붙는다. 원본은 `cozy describe --json`의 `screens[].bindings[]`다([cli.md](cli.md)).
    - **어느 줄에 붙는가**: 요소의 화면 줄(`screenLine`. 넣은 fragment의 요소면 화면 템플릿에서 넣은 줄)을 담는 가장 안쪽 줄이다. 어느 줄에도 담기지 않는 요소도 있으므로, 아무것도 선택하지 않았을 때의 화면 속성에는 화면의 모든 요소가 같은 구획으로 보인다.
    - **요소마다**: 요소(여는 태그와 `templates/…:줄`. 위치는 그 템플릿의 소스 보기 그 줄로 가는 링크), 컴포넌트(누르면 명세가 펼쳐진다. 앱 컴포넌트는 목적, 상태, 계산, 동작, 받는·내는 화면 이벤트와 **고치기**(동작 고치기로), 프레임워크 컴포넌트는 목적, 받는 `data-*`, 메서드. 명세를 모르면 "명세 없음"), 붙은 것 한 줄씩(`이벤트 input → count`, `글자 label`, `넘기는 값 data-limit = 5000`), htmx 속성(`htmx th:hx-post = @{/memo}`, 읽기 전용).
    - **붙이고 떼기**: 앱 템플릿의 요소이고 컴포넌트의 명세가 있으면 붙은 것마다 **떼기**가, 요소 아래에 **붙이기** 폼이 있다. 둘 다 `cozy attach <component> --at <template>:<line> …`(떼기는 `--detach`)의 변경 파일을 오른쪽 칸 위에 보이고 **적용**한다. 명령이 거절하면(컴포넌트에 없는 이름 등) 이유를 보이고 파일은 바뀌지 않는다.
    - **붙이기 폼**: 붙인 자리면 컴포넌트가 읽는 `data-*`마다 칸이 있고(명세의 `@data-*`, 프레임워크 명세의 `data`. 지금 값으로 채운다), 지금 값과 다른 칸만 `--data 이름=값`으로 넘긴다. 그 아래에 붙일 것 하나(이벤트, 글자, 보임, 속성, 입력값, 준비 전 숨김), 이벤트나 속성 이름, 이름이다. 앱 컴포넌트의 이름은 선택 칸(묶음 "동작"과 "상태와 계산")이고, 프레임워크 컴포넌트는 인자를 받는 메서드(`toggle('filter')`)가 있어 글 칸과 쓸 수 있는 이름의 안내다.
    - **요소에 붙이기**: 미리보기에서 앱 템플릿이 그린 요소를 고르면 오른쪽 칸 아래에 **요소에 붙이기**가 보인다(프레임워크 템플릿의 요소와 구조의 줄에는 없다). 누르면 `?at=템플릿:줄`로 오른쪽 칸 위에 붙이기 카드가 열린다(여는 태그, 소스 위치).
      - 요소에 컴포넌트가 붙어 있거나 감싸는 요소의 컴포넌트가 있으면 그 컴포넌트의 붙이기 폼이다("…의 안쪽 요소입니다").
      - 없으면 **붙일 컴포넌트**를 고른다: 그 템플릿 모듈의 앱 컴포넌트와 프레임워크 컴포넌트(모듈 컴포넌트는 그 모듈의 템플릿에만 붙는다). 고르면(`&component=이름`) 목적과 "이 요소가 …의 자리가 됩니다(x-data)", 그리고 `data-*` 칸이 있는 붙이기 폼이 보인다. 붙일 것은 "붙일 것 없음"(`x-data`와 `data-*`만)일 수 있다.
      - `cozy attach`가 거절하는 요소(그 줄에서 시작하는 요소가 없거나 둘 이상, `th:replace`와 `th:block`처럼 그려질 때 바뀌는 요소, 명세가 없는 컴포넌트를 붙인 요소)는 명령과 같은 이유를 보이고 폼이 없다. 원본은 cozy-cli의 `Attach.place`(명령과 같은 판단)다.
      - 카드에서 보낸 것이 거절되면 결과와 함께 카드가 다시 열린다. 확인 결과의 **취소**도 카드로 돌아간다.
    - **쓰는 요청**: 흐름과 조건은 매개변수 수정과 같다(`POST /cozy/dev/workbench/attach`). `option`은 비었거나 `on`, `text`, `show`, `bind`, `model`, `cloak`, `data`(떼기) 가운데 하나다. `data.이름`의 이름은 소문자와 `-`다. 아니면 400이다. `at`은 앱 템플릿:줄 모양이 아니면(`cozy/…`, `..`) 400, 없는 템플릿이면 404, 프로젝트 폴더에서 실행하지 않으면 409다.
    - **명령 복사**: 셸이 펼치는 글자(`$`, `` ` ``)가 있는 인자는 작은따옴표로 감싼다(`--data 'length=${bodyLength}'`). 터미널에 붙여 넣은 명령이 같은 일을 한다.
    - 줄인 표기(`@click`, `:disabled`)와 이 명령이 쓰지 않는 속성(`x-init`, `x-ref` 등)은 보이기만 하고 떼기가 없다.

## 화면

| 주소 | 보이는 것 | 원본 |
| --- | --- | --- |
| `/cozy/dev/workbench` | 개요: 숫자 카드(화면, 모듈, 규칙 위반, 미구현 항목), 모듈별 화면 목록, 규칙 위반, 모듈, 미구현 항목 | 화면 명세, `cozy check --json`, `cozy describe --json` |
| `/cozy/dev/workbench?spec=…` | 화면: 구조, 미리보기, 소스 | `cozy describe --json`, 패턴 카탈로그의 미리보기 |
| `/cozy/dev/workbench/search?q=…` | 검색: 화면, 화면 안의 동작, 화면 이벤트, 컴포넌트, 생성 항목, 모듈 | 화면 명세, 매니페스트, `cozy recipes --json`, `cozy describe --json` |
| `/cozy/dev/workbench/check` | 검사: 파일마다 위반, 고치는 법, 고치는 명령 | `cozy check --json` |
| `/cozy/dev/workbench/commands` | 코드 생성: 생성 항목마다 폼, 변경 파일 확인, 적용 | `cozy recipes --json`, `cozy add·link·enable … --json` |
| `/cozy/dev/workbench/map` | 모듈: 의존성 다이어그램이나 표, 선택한 모듈의 속성(의존 모듈·참조하는 모듈·공개 API·이벤트·이벤트 리스너·화면), 미구현 항목 | `cozy describe --json` |

- **개요**: 워크벤치의 첫 화면이다.
  - 화면 목록은 모듈마다 접고 펴는 묶음이다(모듈 이름, 화면 수, 위반 수). 화면이 12개 이하면 모두 펼치고, 많으면 위반이 있는 모듈만 펼친 채 열고 그렇다고 알린다.
  - 화면마다 상태 이름, 위반 수, "상태 비교"(상태가 둘 이상일 때, `?spec=…&compare=true`)가 붙는다. 이름은 화면 보기로 간다.
  - 규칙 위반은 앞의 5건(규칙 이름, `오류 R3`, `파일:줄`)만 보이고 나머지 수를 알린다. 화면 파일의 위반은 소스 보기 그 줄로 간다. 위반이 없으면 "위반이 없습니다."다.
  - 모듈은 이름(모듈 화면으로), 요약(`화면 4 · 인터페이스 2 · 이벤트 1`), 의존 모듈, 참조하는 모듈이다.
  - 미구현 항목은 앞의 10건을 채울 내용과 `파일:줄`로 보인다. C13은 동작 명세의 컴포넌트 줄과 할 일(붙이기, 잇기, 지우기)이다(`cozy describe --json`의 `slots[]`).
  - 앱 프로젝트 폴더에서 실행하지 않으면 화면 목록만 보이고 나머지는 이유를 알린다.
- **검색**: 머리의 검색 칸(모든 화면에 있다, 글을 적는 중이 아니면 `/`로 옮겨 간다)이나 검색 화면의 칸에 적는다.
  - 찾는 곳: 화면(화면 명세의 `title`, 식별자, 템플릿), 컴포넌트(매니페스트의 `label`, id, `purpose`, signature. 패턴, 아이콘, 레이아웃, 앱 공개 fragment도 여기에), 화면 안의 동작(동작 명세의 컴포넌트 이름, 목적, 상태·계산·동작의 이름), 화면 이벤트(`모듈:이름`), 생성 항목(`title`, 명령, 설명), 모듈(이름, 패키지).
  - 검색어는 공백으로 나눈 낱말이고 모든 낱말이 한 항목 안에 있어야 한다. 대소문자, 띄어쓰기, 식별자의 구분 글자(`- _ / . :`)는 보지 않는다(`메모목록` → 메모 목록, `memolist` → memo-list). 100자에서 자른다.
  - 이름과 식별자에서 먼저 찾는다. 거기서 하나도 찾지 못했을 때만 설명과 경로에서 찾고 "설명에서 찾았습니다"를 알린다. 설명에 낱말이 들어 있을 뿐인 항목이 섞이지 않게 한다(`crud`는 CRUD 화면 하나).
  - 결과는 화면, 화면 안의 동작, 화면 이벤트, 컴포넌트, 생성 항목, 모듈 순서로 묶는다. 묶음 안에서는 이름이나 식별자와 같은 것, 그것으로 시작하는 것, 그것을 품은 것 순서다(`WorkbenchSearch`).
  - 결과는 화면 보기, 패턴 카탈로그의 그 항목(`/cozy/dev/catalog#fragment-component-badge`), 그 생성 항목의 폼, 모듈 화면(동작은 그 컴포넌트 `#behavior-memoBodyCount`, 화면 이벤트는 그 줄 `#ui-event-memo-archived`)으로 간다. 찾은 것이 없으면 "검색 결과 없음"이다.
- **검사**: 위반의 문구와 고치는 명령은 `cozy check`가 내는 것과 같다. 명령 옆의 "복사"로 클립보드에 넣는다.
  - **계획 버튼**: 고치는 명령이 `cozy sync behaviors`(C12)나 `cozy migrate behaviors`(C12 경고)면 **변경 파일 확인**이 있다(개요의 위반에도). 누르면(`POST /cozy/dev/workbench/check`, `fix`는 `sync-behaviors`, `migrate-behaviors`) 검사 화면 위에 변경 파일과 바뀐 줄, 옮기기의 **남은 일**(`파일:줄`, 무엇이 낱말 밖인지, 그 코드)이 보이고 **적용**한다. 그 밖의 명령은 워크벤치가 실행하지 않는다. 쓰는 요청의 조건은 코드 생성과 같다(모르는 `fix`는 400).
  - **C13 항목**은 고치는 화면으로 이어진다(`직접 수정` 대신): 붙이지 않은 컴포넌트는 **붙일 화면**(모듈 화면의 화면 목록 `#module-screens`, 화면을 열고 미리보기에서 요소를 골라 붙인다)과 **동작 고치기**(지우기), 부르지 않는 동작은 **붙인 곳**(`#behavior-…`)과 **동작 고치기**, 받거나 내는 곳이 없는 화면 이벤트는 **동작 고치기**(받는 화면 이벤트, 동작의 `emit`)와 **화면 이벤트**(`#ui-event-…`).
  - 화면 템플릿이나 스펙의 위반은 줄 번호가 워크벤치의 소스 보기 그 줄로 이어진다.
  - 화면 목록에는 화면마다 위반 수가, 머리의 "검사"에는 전체 오류 수가 붙는다.
  - 검사하지 못하면(`cozy check`의 종료 코드 2) 이유를 그대로 보인다.
- **프레임워크 템플릿**: 워크벤치는 실행 중인 cozy-ui의 jar나 클래스 폴더를 cozy 명령에 `--ui`로 넘긴다. Maven 저장소를 찾지 않고, 앱이 지금 쓰는 프레임워크 템플릿으로 검사한다.
- **모듈**: 아래 "모듈 화면"에 적었다. 화면은 워크벤치의 그 화면으로 이어진다. 미구현 항목은 `파일:줄`과 채울 내용으로 보인다.

## 모듈 화면

`/cozy/dev/workbench/map`은 왼쪽에 모듈 의존성, 오른쪽에 속성을 보인다. 원본은 `cozy describe --json` 하나다.

| 파라미터 | 값 | 기본 |
| --- | --- | --- |
| `module` | 선택한 모듈 이름 | 없음 (앱의 속성이 보인다) |
| `view` | `diagram`(다이어그램), `table`(표) | `diagram` |
| `source` | `behavior`(동작 명세), `script`(만든 JS). 선택한 모듈의 그 소스를 의존성 위에 연다. 동작 명세가 없는 모듈이면 404 | 없음 |

- 없는 `module`은 404, 목록에 없는 `view`와 `source`는 400이다.
- **다이어그램**: 서버가 좌표를 계산해(`ModuleGraph`) SVG로 그린다. 스크립트와 외부 라이브러리가 없다.
  - 참조하는 모듈이 왼쪽 열, 참조되는 모듈이 오른쪽 열이다. 의존하는 모듈이 없는 모듈이 맨 오른쪽이다.
  - 실선은 의존이다(`allowedDependencies`). 화살표가 가리키는 모듈을 참조한다. 열을 건너뛰는 선은 사이의 마디를 피해 아래로 휜다.
  - 점선은 이벤트다. 발행하는 모듈에서 수신하는 모듈로 가고 이벤트 이름이 붙는다. 수신하는 모듈은 `listeners[].on`에서 얻는다.
  - 마디에는 모듈 이름과 요약(`화면 4 · 인터페이스 2 · 이벤트 1`)이 있다. 마디는 링크이고 누르면 그 모듈이 선택된다.
  - 모듈을 선택하면 그 모듈에 닿는 선은 짙게, 나머지는 흐리게 보인다. 선의 색은 중립이다.
  - 의존이 순환하면 알림으로 알리고, 순환하는 모듈을 맨 오른쪽 열에 둔다.
  - 이벤트 계약 모듈 `events`는 마디로 그리지 않고, 그쪽으로 가는 실선도 그리지 않는다. 이벤트를 내거나 받는 모듈이 모두 의존하므로, 그리면 한 점으로 모이는 선만 늘고 흐름은 점선이 이미 보인다. 앱에 이 모듈이 있으면 범례가 알린다.
  - 그래서 서로의 이벤트를 받는 두 모듈은 점선이 양쪽으로 그려지고 순환 알림은 나오지 않는다. 의존하는 모듈의 속성 "의존 모듈"에는 `이벤트 계약 모듈 events`가 적힌다.
  - 표 보기, 개요의 모듈 목록, 검색의 모듈도 같은 마디를 쓰므로 `events`가 없다. `/cozy/dev/workbench/map?module=events`는 404다. 코드 생성 화면의 모듈 선택에도 없다(이벤트는 주인 모듈을 고르면 그 자리에 만들어진다).
- **표**: 행은 참조하는 모듈, 열은 참조되는 모듈이다. 칸에 `의존`과 `이벤트 수신: {이벤트}`가 보인다. 모듈이 많거나 화면 낭독기를 쓸 때 본다.
- **속성**: 왼쪽 열이 항목 이름인 표다.

  | 구획 | 항목 |
  | --- | --- |
  | 앱 (선택한 모듈이 없을 때) | 기본 패키지, 메인 클래스, Cozy 버전, 스타터, 모듈 수, 미구현 항목 수 |
  | 기본 정보 | 모듈, 패키지, 의존 모듈, 참조하는 모듈(이 모듈에 의존하는 모듈), 미구현 항목 수 |
  | 공개 API | 명령 인터페이스와 메서드, 조회 인터페이스와 메서드, DTO, 이벤트(필드, 발행 위치, 수신하는 리스너), 공개 프래그먼트 |
  | 이벤트 리스너 | 리스너와 수신 이벤트 |
  | 화면 | 화면 템플릿. 화면 명세가 있으면 화면 보기로 이어진다. 화면이 없으면 그렇다고 알린다(검사의 "붙일 화면"이 오는 곳 `#module-screens`) |
  | 화면 안의 동작 | 동작 명세의 컴포넌트마다 이름, 목적, 붙인 화면과 붙인 요소의 수, 붙인 화면(화면 보기로), 버튼 셋(**고치기**: 동작 고치기로, **동작 명세**: 그 컴포넌트 줄, **만든 JS**. 소스는 `source`로 의존성 위에 연다). 그 아래 화면 이벤트: 이 모듈이 주인이거나 이 모듈에서 내고 받는 화면 이벤트마다 내는 곳과 받는 곳(`memoSelection.pick`, `memo/api/list:12 (htmx)`, `… (서버)`). 동작 명세와 화면 이벤트가 모두 없으면 이 구획이 없다 |

- **미구현 항목**: 화면 아래에 앱 전체의 미구현 항목이 `파일:줄`과 채울 내용으로 보인다.

## 코드 생성

생성 항목을 고르고 폼을 채워 **변경 파일 확인**을 누르면 cozy 명령의 계획(`--dry-run`)이 보이고, **적용**을 누르면 같은 명령을 실행한다. 워크벤치가 파일을 쓰는 곳은 여기뿐이고, 쓰는 것은 cozy 명령이다.

- **목록**: 생성 항목은 `group` 순서로 묶이고 `title`과 명령(`cozy add crud`)으로 보인다.
- **폼**: `cozy recipes --json`의 `params`로 그린다([cli.md](cli.md)의 `parts`, `from`). 통째로 적는 인자는 속성 표(왼쪽 열이 입력 항목 이름과 식별자 `--entity`), 구성이 있는 인자는 그리드다(`CommandForm`).

  | 인자 | 입력 |
  | --- | --- |
  | 자유롭게 적는 값 | 글자 칸. 예시가 칸에 흐리게 보인다 |
  | 고를 값(`choices`)이나 앱의 값(`from`, `strict`) | 선택 칸. 고를 값은 이름 뒤에 값이 붙는다(`대시보드 (overview)`). 모듈에 딸린 값은 모듈마다 묶인다 |
  | 앱의 값을 제안하지만 새 값도 받는 인자(`strict: false`) | 목록이 붙은 글자 칸 (`add crud`·`add screen`의 모듈) |
  | 여럿을 고르는 인자(`separator`) | 체크박스. 고른 값은 선택지 순서로 이어진다(`created,deleted`) |
  | 아이콘(`icons`) | 이름 목록이 붙은 글자 칸. 적은 아이콘이 칸 앞에 그려지고, 아이콘 목록(`/cozy/dev/catalog/icons`)으로 이어진다 |
  | 구성이 있는 인자(`--field`, `--param`, `--nav`) | 그리드. 열이 구성 요소(이름, 종류, 필수, 라벨), 행 하나가 옵션 하나다. 종류는 선택 칸(첫 값이 기본), 필수(`!`)는 체크박스 |

  - **모듈을 고르면** 모듈에 딸린 선택지(엔티티, 이벤트, 인터페이스, DTO)는 그 모듈의 것만 보인다(`workbenchCommand`). 스크립트가 없으면 모든 모듈의 것이 모듈별로 묶여 보인다.
  - **선택지에 없는 값**(지운 엔티티 등)을 보내면 선택 칸 맨 앞에 그 값이 남는다. 명령이 거절하고 이유를 보인다.
  - **그리드의 행**: 여러 번 쓰는 인자만 행을 추가·복제·삭제한다. 행 버튼은 명령을 부르지 않고, 적던 값을 그대로 둔 채 행만 고친 폼을 다시 보이고 그 그리드로 돌아온다. 글을 적는 칸이 모두 빈 행은 넘기지 않는다. 필수 요소가 빈 행은 "필드 2행의 이름"처럼 알린다.
  - 칸에서 Enter를 누르면 "변경 파일 확인"이다.
  - 앱 프로젝트 폴더를 찾지 못하면 앱의 값이 없으므로 모든 칸이 글자 칸이다.
- **폼의 이름**: 통째로 적는 인자는 `arg.{위치 인자}`·`opt.{옵션}`, 그리드의 칸은 `opt.{옵션}.{행}.{구성 요소}`(`opt.field.0.kind`, 행은 0부터)다. 행 버튼은 `row=add:opt.field`, `row=duplicate:opt.field/0`, `row=delete:opt.field/0`이다. 알 수 없는 행 작업이나 없는 행은 400이다.
- **명령**: 폼의 값으로 인자 배열을 만든다. 그리드의 행은 [cli.md](cli.md)의 잇는 규칙으로 값 하나가 된다. 화면에는 터미널에 붙여 넣을 수 있는 글(공백이 있는 인자는 큰따옴표)로 보이고 복사할 수 있다. 셸을 거치지 않는다.
- **변경 파일과 적용 결과**: 변경 파일은 모듈 → 계층 → 파일의 트리다(`ChangeTree`). 모듈마다 구분별 수(`생성 14 · 수정 1`)가 붙고, 모듈과 계층은 접고 편다. 파일은 이름, 모듈 안의 폴더(`spi/dto`), 내용이 보이고 전체 경로는 이름에 마우스를 올리면 보인다. 그 밖에 미구현 항목(`파일:줄`), 수동 수정 항목(파일, 할 일, 넣을 내용. `add field`가 목록이나 상세의 자리를 찾지 못했을 때), 다음 할 일. 문구는 cozy 명령의 것이다.

  | 계층 | 경로 |
  | --- | --- |
  | 공개 API | `{모듈}/spi/**`, `templates/{모듈}/spi/**`, 공개 프래그먼트 매니페스트 |
  | 내부 구현 | `{모듈}/internal/**`의 Java |
  | 화면 | `{모듈}/api/**`, 그 밖의 `templates/{모듈}/**` |
  | 화면 안의 동작 | 동작 명세 `behaviors/{모듈}.yml`과 그 명세에서 만든 `static/{모듈}/{모듈}.js` |
  | SQL | `mapper/{모듈}/**`, `db/migration/V…__{모듈}_….sql` |
  | 화면 명세 | `specs/{모듈}-….yml` |
  | 테스트 | `src/test/**`. 이벤트 샘플(`events/{이벤트}/`)은 그 이벤트의 모듈 |
  | 설정 | 모듈의 `package-info.java`, 그 밖의 파일(`pom.xml` 등) |

  모듈에 딸리지 않은 파일(`pom.xml`, 매니페스트)은 끝의 "앱 공통"에 묶인다.
- **같은 결과**: 폼으로 적용한 것은 같은 명령을 터미널에서 실행한 것과 글자까지 같다. 다시 적용하면 "변경 사항 없음"이다.
- **거절**: 명령이 거절하면(없는 아이콘, 내용이 다른 파일 등) 이유를 보이고 아무 파일도 바꾸지 않는다. 필수 값이 비면 명령을 부르기 전에 알린다.
- **보이는 때**: 파일마다 "바로 보임"(새로고침하면 보인다)이나 "빌드 필요"(앱을 다시 빌드하고 실행해야 보인다)를 붙이고, 결과 아래에 한 줄로 알린다(`바뀐 파일 3개는 새로고침하면 보이고, 2개는 …`). 아래 "바로 보기"를 따른다.
- **바뀐 줄**: 계획이면 파일마다 **바뀐 줄 보기**(`+더한 줄 수 −지운 줄 수`)를 펼쳐 지금 파일과 바뀐 뒤의 글을 줄 단위로 견준다. 바뀐 줄과 앞뒤 세 줄이고, 줄 번호는 지금 파일과 바뀐 뒤의 것 두 칸이다. 더한 줄은 `+`와 success 배경, 지운 줄은 `−`와 critical 배경이고, 화면 낭독기에는 "더한 줄", "지운 줄"로 읽힌다. 원본은 계획의 `plan[].after`([cli.md](cli.md))이고 비교는 cozy-cli의 `LineDiff`다. 256KB가 넘는 파일은 비교 없이 목록만이다. 매개변수 수정과 화면 안의 동작의 결과도 같다.

### 동작 고치기

모듈 화면이나 속성 표의 **고치기**는 `/cozy/dev/workbench/commands?recipe=behavior&edit={컴포넌트}`를 연다. 화면 동작 폼이 그 컴포넌트의 지금 항목(목적, 상태, 계산, 동작, 받는 화면 이벤트)으로 채워진다(`BehaviorEdit`). 원본은 `cozy describe --json`의 `modules[].behaviors[]`다.

- **모듈과 동작**은 주소의 컴포넌트가 정한다. 폼에는 `컴포넌트 memoBodyCount · memo 모듈 · 동작 이름 body-count`로만 보이고 칸이 없다.
- **명령**: 보낸 폼을 지금 항목과 이름으로 견준다.

  | 폼에서 | 명령 |
  | --- | --- |
  | 값을 바꾼 행, 새 이름의 행, 바꾼 목적 | `cozy add behavior <module> <behavior> --computed 이름:식 …` (바뀌지 않은 행은 넘기지 않는다) |
  | 지운 행(지금 있는데 폼에 없는 이름. 두 칸을 비운 행도 같다) | `cozy remove behavior <module> <behavior> --state 이름 …` |
  | 바뀐 것이 없음 | 명령을 부르지 않고 "바뀐 항목이 없습니다" |

  - 두 명령은 **한 계획**이다(cli.md의 "명령 여럿을 한 계획으로"). 결과 칸에 두 명령이 차례로 보이고, 하나라도 거절하면 아무 파일도 바뀌지 않는다. 적용한 파일은 같은 두 명령을 터미널에서 같은 순서로 실행한 것과 글자까지 같다.
  - **순서**: 더하기가 먼저다. 지울 상태를 읽던 계산을 같은 폼에서 고칠 수 있다(`label`이 `text` 대신 같은 글을 만들게 고치고 `text`를 지운다). 지운 이름을 다른 칸에 다시 쓰면(상태 `limit` → 계산 `limit`) 지우기가 먼저다.
  - 지운 항목을 템플릿이 부르면 `remove`가 거절하고 그 줄을 보인다(`템플릿이 부르는 이름입니다: label (memo/internal/fields.html:9)`).
- **낱말 표**: 상태 그리드 아래에 상태의 종류, 계산 그리드 아래에 계산 함수, 동작 그리드 아래에 동작 단계와 이벤트 값이 접힌 표로 있다. 모양(`gt(a, b)`)과 한 줄 설명이다. 새 동작을 만드는 폼에도 있다.
- **칸의 제안**: 상태의 종류, 식, 단계 칸은 글을 적는 칸이고 목록을 제안한다(`datalist`, `cozy recipes --json`의 `strict: false`). 식 칸은 이 컴포넌트의 상태·계산 이름과 계산 함수, 단계 칸은 이름과 동작 단계, 이벤트 값이다.
- **오래된 폼**: 폼에는 연 때의 동작 명세 지문(`specHash`, SHA-256)이 있다. 변경 파일 확인이나 적용 때 지금 명세와 다르면 명령을 부르지 않고 "지금 내용으로 다시 열기"를 보인다.
- **컴포넌트 전체**: 폼 아래의 구획이다.
  - **이름 바꾸기**: 새 동작 이름(소문자와 -)을 적고 변경 파일 확인 → 적용. `cozy rename behavior <module> <behavior> <new-behavior>`이고 붙인 곳의 `x-data`도 바뀐다. 적용하면 새 이름의 폼으로 바뀐다.
  - **컴포넌트 지우기**: 확인 창("컴포넌트 삭제", 지울 컴포넌트 이름) → 변경 파일 확인 → 적용. `cozy remove behavior <module> <behavior>`이고 붙인 곳에서 뗀다. 적용하면 "컴포넌트를 지웠습니다"와 새 동작을 만드는 폼이 보인다.
- **보이는 때**: 동작 명세와 만든 JS, 템플릿만 바뀌므로 적용한 뒤 새로고침하면 미리보기와 화면에 보인다(아래 "바로 보기").

### 쓰는 요청의 조건

| 조건 | 어기면 |
| --- | --- |
| POST이고 CSRF 토큰이 있다 (런타임 기본) | 403 |
| `Origin` 헤더가 있으면 이 앱의 주소와 같다 | 403 |
| 앱 프로젝트 폴더를 찾았다 (행 버튼은 제외. 파일을 쓰지 않는다) | 409 |
| `step`이 `plan`이나 `apply`다 (행 버튼은 `step` 대신 `row`) | 400 |
| `change`가 `edit`(기본), `rename`, `delete` 가운데 하나다 | 400 |
| `edit`는 `recipe=behavior`에만 쓰고, 동작 명세에 있는 컴포넌트다 (GET도 같다) | 400, 404 |

- 쓰는 경로는 cozy 명령의 계획이 정한다. 워크벤치는 경로를 입력받지 않는다.
- "샘플 데이터" 탭의 저장과 상태 복제도 같은 조건을 따른다.

## 샘플 데이터 (fixture 편집)

화면의 "샘플 데이터" 탭(`view=fixture`)은 화면 스펙(`src/main/resources/specs/{화면}.yml`)의 상태 하나에 든 값을 모델의 구조대로 보인다. 고쳐서 **저장**하면 스펙 파일의 그 값만 바뀐다. 워크벤치가 직접 쓰는 파일은 스펙 YAML뿐이다. 이 탭을 열면 오른쪽 칸이 넓어진다(21rem → 28rem).

- **구획**: 상태의 모델마다 하나다. 모델 이름과 타입(`result` `ListResult`)이 제목이다. 검증 오류(`_errors`)도 구획 하나다.
- **타입**: 화면 명세의 `model:`이 가리키는 Java 타입을 실행 중인 앱에서 읽는다. record는 구성 요소, 폼 클래스는 setter가 있거나 public인 필드가 속성이다(선언 순서).
- **속성 이름**: 한글 이름을 앞에, 식별자를 뒤에 쓴다(`제목 title`). 한글 이름은 DTO 소스의 Javadoc에서 읽는다(`SourceDocs`). 설명 전체는 이름에 마우스를 올리면 보인다.

  | 타입 | 읽는 곳 | 이름 |
  | --- | --- | --- |
  | record | 타입 Javadoc의 `@param 이름 설명` | 설명의 괄호·쉼표·마침표 앞까지 (`언제 (yyyy-MM-dd HH:mm)` → `언제`) |
  | 폼 클래스 | 필드 바로 위의 Javadoc (`/** 제목 */`) | 같다 |
  | `CozyPage` | 워크벤치가 아는 이름 (소스가 앱에 없다) | 현재 페이지, 페이지 크기, 전체 건수 |

  - 소스는 `src/main/java`에서 타입의 파일(중첩 타입은 바깥 타입의 파일)을 찾는다. Javadoc이 없거나 읽지 못하면 식별자만 보인다.
  - `cozy add crud`는 화면 DTO(`Row`, `ListResult`, `Detail`)의 `@param`과 폼·필터 필드의 Javadoc을 필드 라벨로 쓴다. `cozy add field`는 `@param` 줄이 있는 record에 새 구성 요소의 줄을 더한다([cli.md](cli.md)).
- **객체는 속성 표**다. 왼쪽 열이 속성 이름과 종류, 오른쪽 열이 입력이다. 객체 안의 객체와 목록은 표 아래에 경로(`page`, `memo/bodyLines`)를 제목으로 따로 보인다.
- **객체의 목록은 그리드**다. 열은 원소 타입의 속성, 행은 목록의 항목이다. 스칼라의 목록은 "값" 열 하나다. 목록이 비어도 열은 보인다. 그리드가 칸보다 넓으면 가로로 스크롤한다.
- **입력**: 타입에 맞는 입력을 쓴다.

  | 타입 | 종류 | 입력 |
  | --- | --- | --- |
  | `boolean`, `Boolean` | true/false | 체크박스 |
  | 정수형(`int`, `long`, `Integer`, `BigInteger` …) | 정수 | 숫자 입력(간격 1) |
  | 실수형(`double`, `BigDecimal` …) | 숫자 | 숫자 입력 |
  | `LocalDate` · `LocalDateTime` · `LocalTime` | 날짜 · 날짜와 시각 · 시각 | 날짜·시각 입력 |
  | enum | 타입 이름 | 상수 가운데 고르는 선택 칸 |
  | 그 밖(`String`, `java.*`) | 텍스트 | 글자 칸 |

  - 지금 값이 입력에 맞지 않으면(체크박스 자리의 `yes`, enum에 없는 이름) 글자 칸으로 보인다.
  - `null`인 값은 빈 칸이고 `null`이 흐리게 보인다. 비워 둔 채 저장하면 바뀌지 않는다.
  - 체크박스는 숨은 `false` 뒤에 놓인다. 끄면 `false`, 켜면 `true`가 간다(같은 이름의 마지막 값).
- **타입을 알 수 없으면**(찾을 수 없는 클래스, `Map`, `Object`, `_errors`) YAML의 모양과 값의 종류대로 묶는다. 찾을 수 없는 클래스는 구획에 이유가 보인다. 목록의 열은 항목들의 키를 모은 것이다.
- **없음**: 타입에는 있는데 명세에 없는 값은 "없음"으로 보인다. 그리드 안의 목록과 객체는 요약(`목록 2개`, `객체`)으로 보인다. 둘 다 여기서 고치지 않는다.
- **자리**: 입력의 이름은 `v.` 뒤에 상태 안의 경로(`result/rows/0/title`)다.
- **행 추가·복제·삭제**: 그리드의 행마다 복제와 삭제 버튼, 그리드 아래에 "행 추가" 버튼이 있다. 모두 저장과 같은 폼의 버튼이어서, 적던 값을 먼저 반영하고 행을 고친 뒤 한 번에 저장한다. 저장한 뒤 그 그리드로 돌아온다(`#fixture-result-rows`).
  - **추가**: 원소 타입의 기본값으로 만든 행을 끝에 더한다. 글은 빈 글, 숫자는 0, 참·거짓은 false, 날짜는 오늘, enum은 첫 상수, 목록은 `[]`다. 원소 타입을 모르면 마지막 행을 복제한다. 타입도 행도 없으면 버튼이 꺼진다.
  - **복제**: 그 행의 글을 그대로 바로 아래에 넣는다. **삭제**: 그 행의 줄을 지운다. 마지막 행을 지우면 `[]`가 된다.
  - 블록 목록(`- …`)은 줄 단위로, 흐름 목록(`[a, b]`)은 괄호 안에서 고친다. 블록 맵의 빈 목록(`rows: []`)에 첫 행을 더하면 블록 목록이 된다. 한 줄에 한 행이 아닌 블록 목록은 고치지 않고 이유를 알린다.
  - 바꾼 뒤에도 저장 전 확인(`ScreenSpec.verify`)을 거친다. 기본값이 모델 타입의 검사(예: `CozyPage`의 페이지는 1 이상)에 걸리면 저장하지 않는다.
  - 칸에서 Enter를 누르면 저장이다. 폼의 첫 제출 버튼은 숨은 저장 버튼이다.
- **값만 바꿔 쓴다**: YAML을 다시 쓰지 않고 파서가 알려 주는 값의 자리만 바꾼다. 주석, 키 순서, 들여쓰기, 다른 값은 글자 그대로 남는다.
  - 글은 글로 남는다. `2026`이나 `true`를 글 자리에 적으면 따옴표로 감싼다. 쌍점, 쉼표, 괄호처럼 YAML이 달리 읽을 글자가 있어도 따옴표로 감싼다.
  - 원래 따옴표가 있던 값은 따옴표를 유지한다.
- **저장 전에 확인한다**: 보인 값과 다른 것만 바꾼다(같은 때를 가리키는 날짜와 시각은 같은 값). 바꾼 값이 종류에 맞는지(정수, 날짜, enum 상수 등) 먼저 보고, 바꾼 스펙을 렌더링 검사와 같은 방법으로 읽고(`ScreenSpec.parse`), 모든 상태의 값을 모델 타입으로 바꿔 본다(`ScreenSpec.verify`). 맞지 않으면 이유를 보이고 쓰지 않는다.
- **폼을 연 뒤 파일이 바뀌었으면** 덮어쓰지 않는다. 다시 열어 고친다.
- **바로 보인다**: 워크벤치가 있으면 화면 스펙을 소스 폴더에서 읽는다(`ScreenSpecs` 빈). 저장한 값이 다시 빌드하지 않아도 미리보기와 패턴 카탈로그에 보인다. 소스 폴더의 스펙을 읽지 못하면 빌드된 스펙을 보이고 이유를 알린다.
- **상태 복제**: 지금 상태의 글을 새 이름으로 바로 아래에 넣는다. 이름은 영문으로 시작하고 영문, 숫자, `-`, `_`만 쓴다. 새 상태는 복제한 뒤 값을 고쳐 만든다.
- **고치지 못하는 것**: 여러 줄 값(`|`, `>`)과 비어 있는 값은 읽기 전용이다. 키를 더하고 빼는 일, 그리드 칸 안의 목록과 객체, 상태를 지우는 일은 스펙 파일에서 한다.

| 요청 | 하는 일 |
| --- | --- |
| `POST /cozy/dev/workbench/fixture` (`spec`, `state`, `hash`, `v.{자리}`) | 값을 저장한다 |
| 같은 요청 + `row=add:{목록}`, `row=duplicate:{목록}/{행}`, `row=delete:{목록}/{행}` | 값을 저장하고 행을 고친다. 행은 0부터. 형식이 다르면 400 |
| `POST /cozy/dev/workbench/state` (`spec`, `from`, `name`, `hash`) | 상태를 복제한다 |

- 쓰는 요청의 조건은 "코드 생성"과 같다(CSRF, 같은 Origin, 프로젝트 폴더). 없는 화면이면 404다. 쓰는 파일은 스펙 폴더 바로 아래의 이미 있는 `{화면}.yml`뿐이다.

## 구조 트리

- 원본은 `cozy describe --json`의 `screens[].outline`이다([cli.md](cli.md)). 워크벤치는 같은 프로세스에서 cozy 명령을 부르고 따로 템플릿을 읽지 않는다.
- 줄마다 표시 이름과 식별자가 보인다(`목록 탐색` `list-with-filter`). 종류(레이아웃, 패턴, 컴포넌트, 영역, 프래그먼트)는 속성 표와 줄의 `title`에 있다.
- 안의 줄은 세로 선으로 이어진다. 안에 줄이 있는 줄은 왼쪽 표식을 눌러 접고 편다(`<details>`). 이름을 누르면 접히지 않고 선택된다. 미리보기에서 접힌 줄 안의 요소를 선택하면 다시 펴진다.
- 줄에 마우스를 올리면 미리보기의 해당 요소가 점선으로 표시된다.
- **삽입**(`th:replace`, `th:insert`): 매니페스트에 있는 fragment는 `label`과 식별자로 보인다. `label`이 없거나 매니페스트에 없으면 종류(`컴포넌트`, `프래그먼트`)와 식별자로 보인다.
- **영역**: 삽입이 `~{::#id}`로 넘기는 요소다. 그 삽입의 파라미터 `label`(`필터 영역`)과 파라미터 이름(`cozyFilter`)으로 보인다.
- **프래그먼트 선언**(`th:fragment`)은 `프래그먼트`와 이름으로 보인다.
- 아이콘은 구조가 아니므로 뺀다. 줄마다 `templates/{템플릿}.html:{줄}`이 붙는다.

## 요소에서 소스로

미리보기에서 요소를 누르거나 구조 트리의 이름을 누르면 오른쪽 칸에 그 항목의 속성(소스 위치, 상위 경로 포함)이 보이고, 트리의 해당 줄이 함께 선택된다.

- **요소 선택** 스위치가 켜져 있으면 미리보기의 클릭이 선택이 된다(링크와 버튼이 동작하지 않는다). 끄면 미리보기가 보통 화면처럼 동작한다.
- **위치**: 화면 템플릿의 `src/main/resources/templates/{템플릿}.html:{줄}`이다.
  - 화면 템플릿의 요소면 그 요소의 줄이다.
  - 프레임워크나 다른 모듈의 fragment가 그린 요소면, 화면 템플릿에서 그 fragment를 넣은 줄이다. 실제로 그린 템플릿과 줄은 "렌더링한 템플릿"으로 함께 보인다.
  - 넣은 fragment가 다시 넣은 fragment가 그린 요소(패턴 안의 제목 등)는 가까운 삽입을 고르고 "삽입 위치는 추정"이라고 알린다.
- **경로 복사**는 `파일:줄`을, **에이전트용 복사**는 아래 글을 클립보드에 넣는다. 클립보드를 쓸 수 없으면 글을 펼쳐 골라 둔다.

```text
Screen: memo-list (state: default)
Element: <td class="text-secondary text-nowrap"> "2026-11-06 10:00"
Source: src/main/resources/templates/memo/api/list.html:50
Inside: app-shell (레이아웃) > list-with-filter (패턴) > cozyResult (#result) > result (fragment 선언) > data-table (컴포넌트)
Spec: src/main/resources/specs/memo-list.yml
Playbook: .agents/skills/cozy-helper/references/screens/PLAYBOOK.md
```

- 다른 템플릿이 그린 요소면 `Rendered by: …` 줄이, 추정이면 `Note: …` 줄이 더 붙는다.
- IDE를 띄우지 않는다. 위치를 복사해 IDE의 "파일로 이동"에 붙인다.

### 위치를 싣는 방법

- 워크벤치는 미리보기를 `/cozy/dev/catalog/screen?…&inspect=1`로 부른다. 이 요청에서만 요소마다 `data-cozy-src="{템플릿}:{줄}"`이 붙는다(`SourceLocationDialect`).
- **그 밖의 HTML은 달라지지 않는다.** `inspect`가 없는 미리보기(렌더링 검사가 부르는 것), 앱 화면, 카탈로그의 fragment 미리보기에는 붙지 않는다. `inspect`가 있는 응답도 이 속성을 빼면 없는 응답과 같다.
- **줄 번호 보정**: Thymeleaf는 파서 주석(`<!--/* … */-->`)을 줄바꿈까지 지운 뒤 읽으므로, 여러 줄짜리 파서 주석 뒤의 줄 번호가 당겨진다. 워크벤치가 템플릿 원문으로 실제 줄을 되찾는다(`SourceLines`). 파서 주석과 같은 줄에서 시작하는 요소는 주석 앞에 있다고 본다.
- 감싸는 구조는 `describe`의 `outline`에서 줄이 `line`~`endLine` 안에 드는 마디다.

## 화면 규칙

워크벤치 자신의 화면도 Tabler 구조와 [design.md](design.md)를 따른다. 인라인 스크립트와 스타일이 없고, 보정은 `cozy.css`의 `cozy-workbench-*`에 있다. 스크립트는 `/cozy/workbench.js` 하나이고 워크벤치 화면에서만 읽는다.

### 화면 안의 동작 (Alpine)

`workbench.js`는 Alpine 컴포넌트를 등록만 한다. 템플릿이 `x-data`와 `x-on`으로 붙인다. 컨트롤러가 모델에 `cozyScripts`를 넣어, 레이아웃이 이 파일을 Alpine보다 먼저 싣는다.

| 컴포넌트 | 자리 | 하는 일 |
| --- | --- | --- |
| `cozyDisclosure` (cozy-ui) | 칸 묶음을 감싼 틀(`.cozy-workbench-layout`, `display: contents`) | 왼쪽 칸(`side`)과 오른쪽 칸(`inspector`) 접기 |
| `cozyCopy` (cozy-ui) | 명령 복사 버튼(검사, 코드 생성, 매개변수 결과) | `data-copy-text` 복사 |
| `cozyFocusKey` (cozy-ui) | 머리의 검색 칸 | `/`를 누르면 검색 칸으로 |
| `workbenchPicker` | 칸 묶음(`.cozy-workbench-panes`) | 미리보기 요소와 구조 트리 잇기, 속성 표, 에이전트 전달 내용, 오른쪽 칸의 스크롤 지키기 |
| `workbenchCompare` | 상태 비교 창 | 고른 상태만 보이기, 4개까지, 창이 열리면 미리보기 불러오기, 너비 |
| `workbenchThumb` | 축소 미리보기 | 칸 폭에 맞게 줄이기 |
| `workbenchCommand` | 코드 생성의 폼과 결과(`#workbench-command`) | 모듈별 선택지, 아이콘 미리보기, 결과로 옮기기 |

- **앱 화면에도 쓸 동작은 `cozy` 컴포넌트다.** `workbench…` 컴포넌트는 워크벤치에만 있는 동작이다. R16은 앱 템플릿이 `workbench…`를 쓰면 오류로 본다.
- **htmx가 바꾸는 칸의 요소는 `x-ref`로 그때마다 찾는다.** `workbenchPicker`는 htmx가 바꾸지 않는 칸 묶음에 있어서, 바뀐 칸의 `x-on`도 같은 컴포넌트를 부른다. 오른쪽 칸이 바뀌면 `x-init="restore"`가 이전 선택을 지우고, `node`(매개변수를 고친 줄)가 있으면 그 줄을 다시 고른다.
- **미리보기(iframe) 안의 문서는 Alpine이 닿지 않는다.** 그 문서와 창에만 이벤트를 직접 단다(`attach`, 미리보기가 그려질 때 `x-on:load`).
- **남기는 데이터 속성**: 구조의 줄(`data-cozy-line`, `-end`, `-kind`, `-target`, `-name`, `-code`), 줄에 딸린 속성 표(`data-cozy-workbench-node-props`, `data-cozy-prop`), 미리보기 요소의 `data-cozy-src`, 선택지의 `data-cozy-module`. 동작을 붙이지 않고 컴포넌트가 읽는다.
- `WorkbenchScriptTest`가 확인한다: 스크립트는 `alpine:init`과 미리보기 문서 말고는 이벤트를 직접 달지 않고, 컴포넌트 이름은 `workbench`로 시작하고, 템플릿에 동작용 `data-cozy-*`가 없다.

### 부분 갱신 (htmx)

서버를 거치는 동작은 htmx가 받은 화면에서 바뀐 영역만 바꾼다. 서버는 htmx 요청에도 같은 응답(리다이렉트, 전체 화면)을 돌려준다. 그래서 스크립트가 없으면 같은 링크와 폼이 전체 페이지로 동작하고, 쓰는 파일은 어느 쪽이든 같다.

| 영역 (id) | 내용 |
| --- | --- |
| `workbench-flash` | 알림(플래시, 스펙을 읽지 못함, 프로젝트 폴더 없음) |
| `workbench-side` | 화면 목록과 구조 트리 |
| `workbench-center` | 미리보기나 소스 |
| `workbench-inspector` | 속성이나 샘플 데이터 |
| `workbench-compare` | 상태 비교 창의 자리 |
| `workbench-errors` | 머리의 "검사" 링크(오류 수) |
| `workbench-command` | 코드 생성의 폼과 결과 |
| `workbench-results` | 검색 결과 |

| 동작 | 바꾸는 영역 | 주소 |
| --- | --- | --- |
| 상태, 화면 너비 | center, inspector, flash, compare | 새 주소를 남긴다 |
| 샘플 데이터 저장, 행 버튼, 상태 복제 | inspector, center, flash, compare | 리다이렉트된 주소 |
| 매개변수 변경 파일 확인, 적용, 취소 | inspector, side, flash, errors | 리다이렉트된 주소 |
| 코드 생성의 변경 파일 확인, 적용, 행 버튼 | command | 그대로 |
| 검색(입력하는 동안 300ms 뒤, 검색 버튼) | results | 검색어를 남긴다 |

- **리다이렉트하는 폼**은 `hx-headers='{"X-Cozy-Redirect": "follow"}'`를 단다. cozy-ui는 htmx 요청의 `redirect:`를 `HX-Redirect`로 바꾸는데, 이 헤더가 있으면 바꾸지 않는다([ui.md](ui.md)의 리다이렉트). 브라우저가 리다이렉트를 따라가 다음 화면(플래시 포함)을 받고, htmx는 `hx-select`·`hx-select-oob`로 고른 영역만 바꾼다.
- **매개변수는 미리보기를 바꾸지 않는다.** 템플릿을 고친 결과는 다시 빌드해야 보이기 때문이다.
- **바뀐 영역은 Alpine이 새로 초기화한다.** 오른쪽 칸을 바꾸는 요청은 그 칸의 스크롤 위치를 지킨다(`workbenchPicker`의 `keepScroll`, `restoreScroll`). 코드 생성에서 변경 파일 확인과 적용은 결과로 옮기고, 행 버튼은 그 자리에 둔다(응답에 결과가 없다).
- **선택한 화면과 상태**(`data-screen`, `data-state` 등)는 오른쪽 칸에 있다. 상태가 바뀌면 함께 바뀌어 에이전트 전달 내용이 새 상태를 가리킨다.
- `WorkbenchHtmxTest`가 확인한다: htmx 요청마다 같은 주소의 `href`·`action`이 있고, 바꿀 영역의 id가 화면에 하나씩 있고, 받은 화면에서 같은 영역을 고른다.
