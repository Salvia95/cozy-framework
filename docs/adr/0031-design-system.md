# ADR-0031 디자인 시스템: Tabler 구현 + Polaris 원칙 + Cloudscape CRUD 흐름

- 상태: 승인 (2026-11-06, 사용자 결정 "권장안으로 갈게")
- 출처: 사용자 지적 "카탈로그에 디자인 원칙(그리드 가운데 정렬, 왼쪽 위 → 오른쪽 아래 흐름)이 없고 색 대비도 원칙이 없다". 사용자 지시 "Tabler layout, Shopify Polaris, Cloudscape의 C/R/U/D 패턴을 조합해 현재 시스템에 맞는 디자인 시스템을 정의". ADR-0014(Tabler·htmx), ADR-0021(UI 구성), ADR-0030(화면 품질)을 잇는다.

## 배경

측정한 결과(2026-11-06) 화면에 원칙이 없었다.

- **색**:
  - 글자 625개 중 38개가 WCAG 2.2 AA(4.5:1)에 못 미쳤다. 연한 배지(4.33:1), 위험색 글자(3.25~4.47:1)가 그랬다.
  - 숫자 카드의 primary·azure·green처럼 의미 없는 색을 템플릿마다 골랐다.
- **흐름**:
  - 폼의 저장 버튼이 왼쪽 아래에 있었다.
  - 상세 화면의 삭제가 가장 강조되는 맨 오른쪽에 있었다.
  - 상세와 수정 폼이 7:5로 나란히 있었다(ADR-0030의 삭제 버튼 중복 결함도 이 구조에서 나왔다).
- **폭**: 새 메모 폼이 12칸 중 왼쪽 8칸에 붙어 있었다.
- **근거 문서**: ADR-0014는 "Tabler를 쓴다"만 정했다. Tabler는 UI 키트라 언제 무엇을 쓰라는 지침이 없다.

## 결정

### 1. 세 출처를 층으로 나눠 쓴다

| 층 | 출처 | 가져오는 것 |
| --- | --- | --- |
| 구현 | Tabler 1.7.3 (MIT, ADR-0014) | CSS, 마크업 구조, 그리드, 간격 단계 |
| 원칙 | Shopify Polaris | 색은 의미에만, 영역마다 주 버튼 하나, 피드백 종류 선택, 대비 4.5:1 |
| 흐름 | AWS Cloudscape | 만들기·상세·수정·삭제 화면 구조, 버튼 문구, 검증 시점, 삭제 확인, 빈 상태와 결과 없음의 구분 |

- **원칙만 가져온다**: 코드, 토큰 값, 아이콘, 문서 문장은 가져오지 않는다.
  - Polaris 코드는 Shopify 연동 앱에만 허락된 라이선스다.
  - Cloudscape 가이드 문서는 "All rights reserved"다(코드는 Apache-2.0).
- **새 의존성 없음**: ADR-0017 표는 바뀌지 않는다.

### 2. 출처끼리 다른 곳은 이렇게 정한다 (사용자 결정: 권장안)

| 문제 | 결정 | 이유 |
| --- | --- | --- |
| 수정 방식 | Cloudscape: 상세는 읽기 전용, 수정은 별도 화면(만들기 폼 재사용) | 서버 렌더링(htmx)에는 Polaris의 저장 막대(바뀐 내용 추적)가 맞지 않는다. 상세와 폼을 섞은 구조가 결함을 냈다 |
| 결과 알림 | Cloudscape: 만들기·수정·삭제 결과는 page-body 위쪽 플래시. 토스트는 사소한 확인(복사 등)에만 | PRG(리다이렉트) 흐름과 맞고 사라지지 않는다 |
| 경로 표시 | 상세·만들기·수정 화면 제목 위에 경로(상위 › 현재). "목록" 버튼은 없앤다 | 두 출처 모두 권한다 |
| 밀도 | 보통 하나만. 촘촘함은 v1에서 제외 | 전환 수단과 두 벌의 검증이 필요하다 |

### 3. 원칙은 `docs/conventions/design.md`에 두고 컴포넌트와 검사로 지킨다

- **색**:
  - 조작(파랑 primary)과 tone 다섯 가지(neutral, info, success, warning, critical)만 쓴다.
  - tone 토큰은 `cozy.css`의 `--cozy-*`에 있고, 대비는 모두 5.8:1 이상이다.
  - 분류는 neutral로 쓴다. 상태 색 외의 장식 색은 쓰지 않는다.
- **흐름**:
  - 제목은 왼쪽 위, 주 동작은 오른쪽 위에 둔다.
  - 폼 버튼은 오른쪽 아래에 [취소] [주 버튼] 순서로 둔다.
  - 상세 머리 버튼은 [삭제] [수정] 순서다.
  - 버튼 묶음마다 주 버튼은 하나이고 맨 오른쪽에 둔다.
- **폭**: 목록·상세·개요는 `container-xl`, 만들기·수정은 가운데 48rem.
- **삭제**: 확인 창을 거친다. 창 제목은 "{대상} 삭제"이고, 대상 이름을 굵게, "되돌릴 수 없습니다"를 쓴다. 버튼은 [취소] [삭제].
- **빈 상태**: 아직 아무것도 없음(만들기 버튼)과 조건에 맞는 것 없음(조건 지우기)을 구분한다.
- **검증**:
  - 입력하는 중에는 검사하지 않는다.
  - 제출 뒤 서버 오류를 칸 아래에 보이고, 첫 오류 칸으로 포커스를 옮긴다.
  - 저장하지 않은 입력이 있으면 떠날 때 확인한다.
- **문구**: 버튼은 "대상 + 동사"(메모 만들기)로 쓴다. 결과 알림은 "메모를 만들었습니다 / 수정했습니다 / 삭제했습니다", 바뀐 게 없으면 "바뀐 내용이 없습니다"다.

### 4. 지키는 방법

- **빌드 규칙(cozy-rules)**:
  - R14: 앱 템플릿이 색 클래스(`bg-*`, `text-red`, `btn-outline-danger` 등)를 직접 쓰면 실패한다. 글자로 쓴 tone이 다섯 가지가 아니어도 실패한다. 허용은 `text-secondary`, `text-muted`, `btn-primary`뿐이다.
  - R15: 버튼 묶음(`btn-list`)에 주 버튼이 둘 이상이거나 맨 오른쪽이 아니면 실패한다. 프레임워크 템플릿도 같다.
- **화면 확인(runtime-verifier)**:
  - V9: 모든 글자의 대비
  - V10: 주 버튼의 개수와 위치
  - V11: 화면 유형별 폭과 가운데 정렬
- **컴포넌트**: 원칙을 담은 컴포넌트를 둔다(`form-actions`, `delete-confirm`, `noResults`, tone을 받는 `badge`·`alert`·`toast`, 색 없는 `stat`). 앱은 이것을 조합한다.

## 보완 (2026-11-12, 사용자 결정)

- 출처: 사용자 지시 "앱 화면까지 고쳐줘", "일치시켜줘", "field는 평문 입력만을 위한 컴포넌트야 선택은 combobox나 picklist, dropdown 등이 있잖아".
- **입력의 테두리와 포커스를 모든 화면에서 3:1 이상으로**: 체크박스·스위치 테두리(Tabler 기본 1.26:1)를 3:1 이상으로, 입력의 포커스 표시(2.1:1)를 2px primary로 바꾼다. ADR-0038 M28에서는 워크벤치의 폼에만 걸었다. 이제 `cozy.css`의 공통 규칙 하나가 앱, 카탈로그, 워크벤치에 같이 걸리고, 화면마다 따로 고친 포커스 규칙은 없앴다. 꺼진 스위치는 Tabler가 테두리를 투명으로 두어(바탕 1.4:1) 따로 보정했고, 오류 칸에 포커스가 가면 빨간 테두리에 링 하나만 보이도록 Tabler의 오류 outline을 껐다(화면 확인으로 잼). §3의 "아이콘과 경계선 3:1"을 지키는 보정이므로 원칙은 바뀌지 않는다.
- **확인 창의 제목 구조를 하나로**: `modal`(h5), `deleteConfirm`(h3), 워크벤치의 상태 비교 창(h2)이 서로 달랐다. 모두 `role="dialog"`, 제목 `h2.modal-title`, `aria-labelledby`로 맞춘다. 확인 창은 화면 본문 밖의 독립된 맥락이라 화면 제목(`h2.page-title`)과 같은 단계로 둔다. 글자 크기는 Tabler의 `.modal-title`(16px)이 정하므로 보이는 크기는 그대로다.
- **`field`는 직접 적는 입력이다**: 정해진 값 중에서 고르는 칸은 `field`의 type으로 늘리지 않고, 선택 컴포넌트(드롭다운, 콤보박스, 픽리스트)가 맡는다. 켜고 끄는 칸 하나(`checkbox`, `switch`)는 고르기가 아니므로 `field`에 남긴다(사용자 결정: 권장안).

### 이어서 정한 것 (2026-11-12, 사용자 결정 "다 권장안으로 할게")

- **글자 칸의 평소 테두리도 3:1 이상으로**: 글자 칸과 셀렉트의 평소 테두리가 흰 바탕에서 1.26:1로 측정되었다(§3의 "경계선 3:1" 미달). 모든 입력(글자 칸, 셀렉트, 체크박스, 스위치, 입력 앞뒤의 덧붙임)의 테두리를 토큰 `--cozy-control-border`(#8c8c8c, 3.4:1) 하나로 맞춘다. 보조 회색(#666, 5.7:1)은 화면 전체를 눈에 띄게 진하게 만들어 쓰지 않았다. 워크벤치 검색 칸만 따로 진하게 둔 규칙은 없앴다. 앞 항목의 체크박스·스위치도 같은 토큰이다.
- **선택 컴포넌트 두 가지를 먼저 더한다**: 새 의존성 없이 되는 것만 넣는다. 이름은 KRDS 컴포넌트 목록의 "선택" 분류(셀렉트, 체크박스, 라디오 버튼)를 따랐다(2026-11-12, krds.go.kr 컴포넌트 개요에서 확인).

  | 컴포넌트 | 호출 | 구현 |
  | --- | --- | --- |
  | 셀렉트 | `selectField(name, label, options)` | 기본 `<select class="form-select">`, 맨 앞 "선택하세요" |
  | 체크박스 | `checkboxGroup(name, label, options)` | `fieldset` + 체크박스 묶음 (여럿) |
  | 라디오 버튼 | `radioGroup(name, label, options)` | `fieldset` + 라디오 묶음 (하나) |

  - 오류인 체크박스·라디오의 선택지 글자는 Tabler 빨강이 옅은 회색 바탕에서 4.47:1로 측정되어, 칸 오류 글자와 같은 `--cozy-critical-fg`(약 7.2:1)로 바꿨다.
  - 선택지는 새 공개 타입 `CozyOptions`(값과 이름의 목록)로 넘긴다. fragment 이름이 `select`가 아닌 것은 같은 파일의 `<select>` 요소와 겹치지 않게 하려는 것이다(R12).
  - **콤보박스(찾아서 고르기)는 미룬다.** `datalist`는 브라우저마다 모양이 다르고, 라이브러리(Tom Select 등)는 ADR-0017 표와 폐쇄망 반입 검토가 필요하다. 실제로 필요한 화면이 생기면 정한다.
  - **`cozy add crud`의 고르는 값 필드는 이 결정에 넣지 않는다.** 레시피 인자 형식(`--field`의 종류)과 저장 형식을 바꾸는 일이라 ADR-0033·0037의 레시피 결정을 따로 개정한다.
- **확인 창의 열리는 모양을 하나로**: Tabler의 모달 마크업(`modal modal-blur fade`, `aria-hidden="true"`)을 따른다. 워크벤치의 상태 비교 창이 이미 이 모양이었고, `modal`과 `deleteConfirm`을 맞췄다.

### 그리드와 표의 머리 (2026-11-12, 사용자 지시 "헤더성 데이터는 가운데 정렬로 해줘", "그리드 내 입력의 경우 보더라인이 없이, 셀 전체를 영역으로 하는 입력으로 해줘", "컬럼별 입력 방식은 … 개발자가 선택하도록 하자". 범위는 사용자 결정: cozy-ui 컴포넌트, 머리 정렬은 모든 표)

- **표의 머리는 가운데**: 열 머리, 행 머리(속성 표의 항목 이름), 행 번호처럼 항목을 나타내는 `th`는 가운데 정렬, 값 칸은 왼쪽이다. 왼쪽 정렬된 머리가 값과 섞여 읽기 어렵다는 지적이었다. `cozy.css`의 `.table th` 규칙 하나가 앱 표(`dataTable`), 워크벤치의 속성 표와 그리드에 같이 걸린다.
- **입력 그리드 컴포넌트 `inputGrid(label, grid)`를 더한다**: 같은 모양의 여러 행을 표에서 바로 입력한다. 화면 유형이 아니라 만들기·수정 폼 안의 컴포넌트다.
  - 칸 전체가 입력이다. 입력의 테두리를 없애고 칸의 선을 입력 테두리 토큰(3:1)으로 긋는다. 포커스는 이웃 칸을 덮지 않게 칸 안쪽 2px 링이다.
  - 열마다 입력 방식을 개발자가 고른다: text, number, date, email, select(셀렉트, 흔히 콤보박스라 부르는 것), radio, checkbox. 공개 타입 `CozyGrid`(열, 행, 칸의 입력 이름·값·오류)로 넘기고, Spring 폼의 목록 속성은 `CozyGrid.bind`로 만든다.
  - 행 추가·복제·삭제는 워크벤치가 쓰던 약속(`row=add:{그리드}`, `duplicate:{그리드}/{행}`, `delete:{그리드}/{행}`)을 그대로 공개하고, 컨트롤러는 `CozyGrid.RowAction`으로 처리한다. 저장 전 목록의 행이라 확인 창 없이 지운다.
- **워크벤치의 그리드(코드 생성의 반복 입력, 샘플 데이터의 목록)는 같은 모양을 쓴다**: 표에 `cozy-grid`를 붙여 머리, 행 번호, 칸 입력, 행 작업 칸이 입력 그리드와 같다. 칸을 그리는 템플릿은 워크벤치 것을 그대로 쓴다. 고정 값, 없는 값, 아이콘 고르기, 시각 입력처럼 입력 그리드가 다루지 않는 칸이 있기 때문이다.
