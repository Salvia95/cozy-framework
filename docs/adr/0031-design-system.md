# ADR-0031 디자인 시스템: Tabler 구현 + Polaris 원칙 + Cloudscape CRUD 흐름

- 상태: 승인 (2026-11-06, 사용자 결정 "권장안으로 갈게")
- 출처: 사용자 지적 "카탈로그에 디자인 원칙(그리드 가운데 정렬, 왼쪽 위 → 오른쪽 아래 흐름)이 없고 색 대비도 원칙이 없다". 사용자 지시 "Tabler layout, Shopify Polaris, Cloudscape의 C/R/U/D 패턴을 조합해 현재 시스템에 맞는 디자인 시스템을 정의". ADR-0014(Tabler·htmx), ADR-0021(UI 구성), ADR-0030(화면 품질)을 잇는다.

## 배경

측정한 결과(2026-11-06) 화면에 원칙이 없었다.

- **색**:
  - 글자 625개 중 38개가 WCAG 2.2 AA(4.5:1)에 못 미쳤다. 연한 배지(4.33:1), 위험색 글자(3.25~4.47:1)가 그랬다.
  - 숫자 카드의 primary·azure·green처럼 의미 없는 색을 템플릿마다 골랐다.
- **흐름**:
  - 폼의 저장 버튼이 왼쪽 아래에 있었다.
  - 상세 화면의 삭제가 가장 강조되는 맨 오른쪽에 있었다.
  - 상세와 수정 폼이 7:5로 나란히 있었다(ADR-0030의 삭제 버튼 중복 결함도 이 구조에서 나왔다).
- **폭**: 새 메모 폼이 12칸 중 왼쪽 8칸에 붙어 있었다.
- **근거 문서**: ADR-0014는 "Tabler를 쓴다"만 정했다. Tabler는 UI 키트라 언제 무엇을 쓰라는 지침이 없다.

## 결정

### 1. 세 출처를 층으로 나눠 쓴다

| 층 | 출처 | 가져오는 것 |
| --- | --- | --- |
| 구현 | Tabler 1.7.3 (MIT, ADR-0014) | CSS, 마크업 구조, 그리드, 간격 단계 |
| 원칙 | Shopify Polaris | 색은 의미에만, 영역마다 주 버튼 하나, 피드백 종류 선택, 대비 4.5:1 |
| 흐름 | AWS Cloudscape | 만들기·상세·수정·삭제 화면 구조, 버튼 문구, 검증 시점, 삭제 확인, 빈 상태와 결과 없음의 구분 |

- **원칙만 가져온다**: 코드, 토큰 값, 아이콘, 문서 문장은 가져오지 않는다.
  - Polaris 코드는 Shopify 연동 앱에만 허락된 라이선스다.
  - Cloudscape 가이드 문서는 "All rights reserved"다(코드는 Apache-2.0).
- **새 의존성 없음**: ADR-0017 표는 바뀌지 않는다.

### 2. 출처끼리 다른 곳은 이렇게 정한다 (사용자 결정: 권장안)

| 문제 | 결정 | 이유 |
| --- | --- | --- |
| 수정 방식 | Cloudscape: 상세는 읽기 전용, 수정은 별도 화면(만들기 폼 재사용) | 서버 렌더링(htmx)에는 Polaris의 저장 막대(바뀐 내용 추적)가 맞지 않는다. 상세와 폼을 섞은 구조가 결함을 냈다 |
| 결과 알림 | Cloudscape: 만들기·수정·삭제 결과는 page-body 위쪽 플래시. 토스트는 사소한 확인(복사 등)에만 | PRG(리다이렉트) 흐름과 맞고 사라지지 않는다 |
| 경로 표시 | 상세·만들기·수정 화면 제목 위에 경로(상위 › 현재). "목록" 버튼은 없앤다 | 두 출처 모두 권한다 |
| 밀도 | 보통 하나만. 촘촘함은 v1에서 제외 | 전환 수단과 두 벌의 검증이 필요하다 |

### 3. 원칙은 `docs/conventions/design.md`에 두고 컴포넌트와 검사로 지킨다

- **색**:
  - 조작(파랑 primary)과 tone 다섯 가지(neutral, info, success, warning, critical)만 쓴다.
  - tone 토큰은 `cozy.css`의 `--cozy-*`에 있고, 대비는 모두 5.8:1 이상이다.
  - 분류는 neutral로 쓴다. 상태 색 외의 장식 색은 쓰지 않는다.
- **흐름**:
  - 제목은 왼쪽 위, 주 동작은 오른쪽 위에 둔다.
  - 폼 버튼은 오른쪽 아래에 [취소] [주 버튼] 순서로 둔다.
  - 상세 머리 버튼은 [삭제] [수정] 순서다.
  - 버튼 묶음마다 주 버튼은 하나이고 맨 오른쪽에 둔다.
- **폭**: 목록·상세·개요는 `container-xl`, 만들기·수정은 가운데 48rem.
- **삭제**: 확인 창을 거친다. 창 제목은 "{대상} 삭제"이고, 대상 이름을 굵게, "되돌릴 수 없습니다"를 쓴다. 버튼은 [취소] [삭제].
- **빈 상태**: 아직 아무것도 없음(만들기 버튼)과 조건에 맞는 것 없음(조건 지우기)을 구분한다.
- **검증**:
  - 입력하는 중에는 검사하지 않는다.
  - 제출 뒤 서버 오류를 칸 아래에 보이고, 첫 오류 칸으로 포커스를 옮긴다.
  - 저장하지 않은 입력이 있으면 떠날 때 확인한다.
- **문구**: 버튼은 "대상 + 동사"(메모 만들기)로 쓴다. 결과 알림은 "메모를 만들었습니다 / 수정했습니다 / 삭제했습니다", 바뀐 게 없으면 "바뀐 내용이 없습니다"다.

### 4. 지키는 방법

- **빌드 규칙(cozy-rules)**:
  - R14: 앱 템플릿이 색 클래스(`bg-*`, `text-red`, `btn-outline-danger` 등)를 직접 쓰면 실패한다. 글자로 쓴 tone이 다섯 가지가 아니어도 실패한다. 허용은 `text-secondary`, `text-muted`, `btn-primary`뿐이다.
  - R15: 버튼 묶음(`btn-list`)에 주 버튼이 둘 이상이거나 맨 오른쪽이 아니면 실패한다. 프레임워크 템플릿도 같다.
- **화면 확인(runtime-verifier)**:
  - V9: 모든 글자의 대비
  - V10: 주 버튼의 개수와 위치
  - V11: 화면 유형별 폭과 가운데 정렬
- **컴포넌트**: 원칙을 담은 컴포넌트를 둔다(`form-actions`, `delete-confirm`, `noResults`, tone을 받는 `badge`·`alert`·`toast`, 색 없는 `stat`). 앱은 이것을 조합한다.

## 결과

- **바뀐 시그니처**:
  - `pageHeader(제목, 상위 이름, 상위 주소, 버튼)`
  - `formPage(제목, 상위 이름, 상위 주소, 폼)`
  - `badge(text, tone)`
  - `stat(icon, value, label)`
  - `alert`·`toast`의 kind는 tone
- **새 것**:
  - 패턴 `details`
  - 컴포넌트 `form-actions`, `delete-confirm`, `no-results`
  - `CozyFlash.critical`(`danger`는 없앤다. 모르는 종류면 예외)
- **없앤 것**: `detailEdit` 패턴
- **이행**: reference-app 메모 화면을 목록, 만들기, 상세, 수정, 삭제 확인으로 나눈다. 아키타입 home과 위반 픽스처(R14, R15)를 맞춘다.
- **문서**: design.md(새 문서), ui.md, rules.md, AGENTS.md, runtime-verifier.md
