# ADR-0037 `cozy add field`: crud 한 벌에 필드 하나 더하기

- 상태: 승인 (2026-11-10, 사용자 결정 "제안대로 승인"). 아래 "정한 것" 여섯 가지
- 출처: 사용자 지시 "내부 평가 결과 반영과 cozy add field까지 진행하자"
- 이어받는 결정: [ADR-0033](0033-stage-two-recipes.md) §1(범위), §2(파서가 찾은 위치), §3(다시 실행)
- 바꾸는 결정:
  - ADR-0033 "정한 것" 4: `field`의 보류를 푼다.
  - ADR-0033 §1 "범위 밖: 메서드 시그니처 바꾸기": crud의 `{E}Facade.create`와 `update` 두 메서드만 예외로 한다(§4).
  - ADR-0036 위험 "이미 있는 화면에 필드를 더하는 일은 워크벤치도 하지 못한다": 명령 폼으로 할 수 있게 된다(§8).

## 배경

- **보류한 이유는 두 가지였다**(ADR-0033 정한 것 4).
  - 고칠 곳이 많고, 에이전트가 이미 고친 곳과 겹친다.
  - 표시(`cozy:append`)를 넣어야 한다고 보았다. 그러면 표시를 넣은 뒤에 만든 crud만 지원한다.
- **표시는 필요 없어졌다.** 2단계 레시피(M12~M14)가 javac 파서와 XML 파서로 위치를 찾는 방식을 이미 쓴다. 같은 방식이면 1.1.0에서 만든 crud에도 쓸 수 있다.
- **고칠 곳을 세어 보았다.** 필드 하나에 17개 파일의 25곳쯤이다.

  | 파일 | 고칠 곳 |
  | --- | --- |
  | 새 마이그레이션 | `ALTER TABLE … ADD COLUMN` |
  | `{E}`(도메인), `{E}Item`(spi DTO) | record 구성 요소 |
  | `{E}Row` | 필드, getter, setter |
  | `{E}Mapper` | `update`의 파라미터 |
  | `{E}Mapper.xml` | `columns`, `insert`의 열과 값, `update`의 `SET` |
  | `{E}Facade` | `create`, `update`의 파라미터 |
  | `{E}FacadeImpl` | 두 메서드의 파라미터, `row.set…`, `mapper.update(…)`의 인자 |
  | `{E}FinderImpl` | `new {E}Item(…)`의 인자 |
  | `{E}Form` | 속성, 검증 애너테이션, getter, setter |
  | `{E}Views` | `Row`·`Detail`의 구성 요소와 `of`의 인자, `formOf`, `unchanged` |
  | `{E}Controller` | `facade.create(…)`, `facade.update(…)`의 인자 |
  | `fields.html`, `list.html`, `detail.html` | 입력 칸, 목록 열, 상세 항목 |
  | 스펙 4개(`list`, `form`, `detail`, `edit`) | 상태마다 값 |
  | `{E}CrudTest`, `{E}ScreenTest` | `create`·`update` 호출의 인자, 폼 파라미터 |

- **스펙의 값은 빠뜨릴 수 없다.** fixture는 record의 구성 요소가 빠지면 실패한다(`FAIL_ON_MISSING_CREATOR_PROPERTIES`). 화면 DTO에 필드를 더하면 스펙도 같이 고쳐야 `mvn verify`가 통과한다.
- **이 일은 작은 모델이 실패하는 종류다.** 여러 파일의 이름, 타입, 순서를 서로 맞춰야 한다(ADR-0032 배경). 한 파일 안에서 열 하나를 더하는 일은 잘한다.

## 결정

### 1. 명령

```text
cozy add field <모듈> --entity <E> --field 이름:종류[!][:라벨] [--default <값>] [--dry-run] [--json]
```

- 필드 형식은 `cozy add crud`와 같다. 종류는 `text`, `longtext`, `int`, `long`, `bool`, `date`다. `instant`는 받지 않는다(crud와 같다).
- 한 번에 필드 하나다. 여러 개면 명령을 여러 번 실행한다. 실패했을 때 무엇이 걸렸는지 메시지 하나로 알 수 있다.
- 대상은 `cozy add crud`가 만든 한 벌이다. 아래 §2의 "꼭 고칠 곳" 파일이 모두 있어야 한다. 하나라도 없으면 crud 한 벌이 아니라고 알리고 실패한다.
- 남기는 빈칸은 없다. 성공한 직후 `mvn verify`가 통과한다(만든 테스트 포함).

### 2. 고칠 곳을 둘로 나눈다

| 묶음 | 대상 | 자리를 찾지 못하면 |
| --- | --- | --- |
| 꼭 고칠 곳 | 마이그레이션, Java 전부, Mapper XML, `fields.html`, 스펙의 값, 테스트의 호출 | 실패한다. 아무 파일도 바뀌지 않는다. 메시지가 파일과 기대한 모양을 알린다 |
| 보이는 곳 | `list.html`의 열, `detail.html`의 항목 | 그 화면만 건너뛴다. 명령은 성공하고, 결과의 `남은 일`에 파일과 넣을 마크업을 싣는다 |

- **나누는 기준**: 빠지면 빌드가 깨지거나 값을 넣을 수 없게 되는 곳은 "꼭 고칠 곳"이다. 빠져도 앱이 맞게 도는 곳은 "보이는 곳"이다.
- **이유**: 목록과 상세의 배치는 에이전트와 사람이 가장 많이 고치는 곳이다. 여기서 못 찾았다고 전체를 실패시키면, 작은 모델이 25곳을 손으로 맞춰야 한다. 한 파일에 열 하나를 더하는 일은 작은 모델이 잘한다.
- `--json`에는 `manual[]`(`file`, `what`, `snippet`)로 싣는다. 비어 있으면 남은 일이 없다.

### 3. 자리 찾기

표시를 쓰지 않는다. 파서가 찾은 위치에 넣는다(ADR-0033 §2).

| 자리 | 넣는 위치 | 확인하는 것 (아니면 실패) |
| --- | --- | --- |
| 도메인·`Item` record | `createdAt` 구성 요소 바로 앞 | record이고 `createdAt`, `updatedAt`이 차례로 끝에 있다 |
| `Views.Row` | `updatedAt` 바로 앞 (`longtext`는 넣지 않는다) | `{E}Views` 안의 record `Row` |
| `Views.Detail` | `createdAt` 바로 앞 (`longtext`는 `List<String> {이름}Lines`) | `{E}Views` 안의 record `Detail` |
| `Row`, `Form` 클래스 | 필드는 마지막 필드 뒤, 접근자는 본문 끝 | 같은 이름의 필드나 접근자가 없다 |
| `Facade`·`FacadeImpl`의 `create`, `update` | 파라미터 목록의 끝 | 이름이 같은 메서드가 하나씩이고 파라미터 수가 인터페이스와 구현에서 같다 |
| `Mapper.update` | `updatedAt` 파라미터 바로 앞 | 마지막 파라미터가 `@Param("updatedAt")`이다 |
| `row.set…` | `row.setCreatedAt(…)` 문 바로 앞 | `create` 안에 그 문이 하나 있다 |
| `formOf` | `return` 문 바로 앞 | `{E}Views.formOf`가 하나 있다 |
| `unchanged` | `return` 식의 끝에 `&& …` | `return` 문이 하나다 |
| Mapper XML `columns` | `created_at` 바로 앞 | `<sql id="columns">`의 열 순서가 도메인 record의 구성 요소 순서와 같다 |
| Mapper XML `insert`, `update` | 열과 값은 `created_at`·`#{createdAt}` 앞, `SET`은 `updated_at =` 앞 | `id`가 `insert`·`update`인 문이 하나씩이고 그 글자가 한 번씩 나온다 |
| `fields.html` | fragment `{e}Fields`의 닫는 태그 바로 앞 | 그 fragment가 하나 있다 |
| 스펙 | §5 | §5 |

- 고친 Java와 XML은 다시 읽어 문법 오류가 없는지 확인한 뒤 적용한다(ADR-0033 §2와 같다).

### 4. 호출하는 곳 (ADR-0033 §1의 예외)

- `create`와 `update`의 파라미터가 늘고, record의 구성 요소가 는다. 그래서 호출하는 곳도 함께 고친다. 시그니처를 바꾸는 일은 범위 밖이었지만(ADR-0033 §1), 이 두 메서드와 crud의 record에만 예외를 둔다.
- **찾는 범위**: 앱의 `src/main/java`와 `src/test/java` 전체.
- **찾는 방법**: javac 파서는 타입을 풀지 않는다. 그래서 이름으로 찾는다.

  | 호출 | 찾는 기준 |
  | --- | --- |
  | `x.create(…)`, `x.update(…)` | 같은 파일에서 `x`가 `{E}Facade` 타입으로 선언된 필드, 파라미터, 지역 변수다 |
  | `x.update(…)` (Mapper) | 같은 파일에서 `x`가 `{E}Mapper` 타입으로 선언돼 있다 |
  | `new {E}Item(…)`, `new {E}(…)` | 그 타입을 import했거나 같은 패키지다 |
  | `new Row(…)`, `new Detail(…)` | `{E}Views.java` 안이거나 `{E}Views.Row`처럼 적혀 있다 |

- **인자 수가 예전 파라미터 수와 다르면 실패한다.** 다른 메서드이거나 이미 손댄 호출이라 판단할 수 없다.
- **넣는 인자**:

  | 호출이 있는 곳 | 옆 인자의 모양 | 넣는 인자 |
  | --- | --- | --- |
  | `src/main` | `r.getX()`, `r.isX()` | `r.get{F}()` (`bool`은 `r.is{F}()`) |
  | `src/main` | `r.x()` | `r.{f}()` (`Detail`의 `longtext`는 `r.{f}().lines().toList()`) |
  | `src/main` | 메서드의 파라미터 이름 | `{f}` (그 메서드에 파라미터를 더했을 때) |
  | `src/main` | 그 밖 | **실패한다.** 어떤 값을 넘길지 판단할 수 없다 |
  | `src/test` | 무엇이든 | 샘플 값 (`cozy add crud`의 테스트와 같은 값) |

- `{E}ScreenTest`의 폼 파라미터(`.param("이름", …)`)는 이름 필드의 `.param(…)` 뒤에 더한다. 그 호출을 찾지 못하면 실패한다.
- **이벤트는 건드리지 않는다.** `--publish`로 만든 이벤트에 새 필드를 실으려면 `cozy add event-version`을 쓴다. 명령이 `다음:`에 알린다.

### 5. 스펙의 값

- 앱의 스펙 전체에서 `model:`의 타입이 `{E}Views.Detail`, `{E}Views.ListResult`, `{E}Form`인 항목을 찾는다. crud의 네 화면이 아니어도 그 DTO를 쓰면 고친다.

  | 모델 타입 | 값을 더하는 곳 | 값 |
  | --- | --- | --- |
  | `Detail` | 상태마다 그 항목의 맵, `createdAt` 앞 | 샘플 값. `longtext`는 `{이름}Lines: []` |
  | `ListResult` | 상태마다 `rows`의 각 맵, `updatedAt` 앞 | 샘플 값 |
  | `Form` | 상태마다 그 항목의 맵이 비어 있지 않을 때, 끝 | 샘플 값 |

- 위치는 SnakeYAML이 읽은 마디의 시작·끝으로 정한다. 흐름 표기(`{ a: 1 }`)와 블록 표기 둘 다 받는다. 나머지 글자(주석, 줄바꿈)는 그대로 둔다.
- 맵이 아니거나(별칭, 글자) 같은 키가 이미 있으면 실패한다.

### 6. 마이그레이션

- 새 파일 `V{시각}__{모듈}_add_{테이블}_{열}.sql`에 `ALTER TABLE {테이블} ADD COLUMN {열} {정의};` 한 줄을 쓴다. 이미 있는 마이그레이션은 고치지 않는다.
- 열 정의는 `cozy add crud`와 같다(`Field.sql()`).
- **필수 필드(`!`)는 `--default`가 있어야 한다**(`bool` 제외). SQLite는 `NOT NULL` 열을 더할 때 상수 기본값이 있어야 하고, 이미 있는 행이 그 값을 갖는다. 없으면 실패하고 `--default`를 쓰라고 알린다.
- `--default`의 값은 종류에 맞는지 확인한다(`int`·`long`은 숫자, `date`는 `yyyy-MM-dd`, 필수 `text`는 빈 글자가 아님). SQL 글자로 바꿀 때 작은따옴표를 겹쳐 쓴다.
- 테이블 이름은 Mapper XML의 `insert` 문에서 읽는다.

### 7. 다시 실행

| 상태 | 결과 |
| --- | --- |
| "꼭 고칠 곳" 어디에도 그 필드가 없다 | 적용한다 |
| "꼭 고칠 곳" 모두에 같은 타입으로 있다 | 바뀐 것 없음 (종료 코드 0). "보이는 곳"은 다시 보지 않는다 |
| 일부에만 있거나 타입이 다르다 | 실패한다. 있는 곳과 없는 곳을 알린다 |

### 8. 워크벤치와 에이전트 문서

- 워크벤치의 명령 폼은 `cozy recipes --json`으로 만든다. 그래서 `field`가 목록에 들어가면 폼이 생긴다. 워크벤치 코드는 바꾸지 않는다.
- Java가 바뀌므로 워크벤치에서는 다시 빌드하고 띄운 뒤에 보인다(ADR-0036과 같다).
- `cozy-helper` 스킬에 `add-field` 플레이북을 더하고 `AGENTS.md`의 명령 표에 한 줄을 더한다. 이미 있는 앱은 `cozy sync agents`로 받는다.

### 9. 하지 않는 것

- **검색 조건**: 새 `text` 필드를 목록 검색(`searchCondition`)에 넣지 않는다. `다음:`에 알린다.
- **필드 지우기, 이름 바꾸기, 종류 바꾸기**: 범위 밖 그대로다.
- **순서 고르기**: 새 필드는 늘 마지막 필드 뒤다.
- **crud가 아닌 모듈**: 손으로 쓴 모듈과 `query`·`command`로 만든 것은 대상이 아니다.

### 10. 완료 기준

- **같은 결과**: `cozy add crud`에 필드 N개를 준 결과와, N-1개로 만든 뒤 `cozy add field`를 한 결과를 비교한다. 종류 여섯 가지마다 한다. 달라도 되는 곳은 표로 고정한다(마이그레이션 파일, 검색 조건과 검색 문구, `longtext`의 상세 배치).
- **레시피 픽스처**: 기본 앱에 `add crud` → `add field` 여섯 번 → `mvn verify`가 통과한다(`samples/recipes`).
- **고친 코드**: reference-app의 memo처럼 메서드 본문을 손으로 고친 crud에 적용해도 통과한다.
- **실패로 닫기**: 자리마다 모양을 깨뜨린 입력에서 실패하고 파일이 하나도 바뀌지 않는다.
- **다시 실행**: 두 번째 실행은 바뀐 것 없음이다.
- **보이는 곳**: `list.html`을 알아볼 수 없게 고친 입력에서 명령이 성공하고 `manual[]`에 그 파일이 실린다.
- **화면**: `runtime-verifier`로 필드를 더한 목록, 만들기, 상세, 수정 화면을 확인한다(ADR-0030).

### M22 구현 메모

- **`Row`의 자리**: 필드는 `createdAt` 필드 앞의 필드 뒤에, 접근자는 `getCreatedAt()` 앞의 접근자 뒤에 넣는다(§3의 "마지막 필드 뒤, 본문 끝"은 `Form`에만 해당한다). crud가 만드는 순서와 같게 하려는 것이다.
- **다시 실행에서 보는 곳**: 도메인, `Item`, `Row`, `Form`, `Views.Detail`, `Facade.create`의 파라미터, Mapper XML의 `columns` 일곱 곳이다.
- **`{E}ScreenTest`**: 폼의 속성을 모두 보내는 `.param(…)` 줄에만 더한다. 이름 필드만 비워 보내는 검증 테스트 줄은 그대로 둔다. 파일이 없으면 건너뛴다.
- **import**: `jakarta.*`는 "그 밖" 그룹이라 crud가 만든 순서(`jakarta` 다음 `org`)와 다른 자리에 들어갈 수 있다. "같은 결과" 테스트는 import 순서를 비교하지 않는다.
- **플레이북**: `AgentDocsTest`가 레시피마다 플레이북을 요구하므로 `add-field` 플레이북을 M22에 넣었다. `AGENTS.md`에는 명령 목록이 없어서 바꾸지 않았다.
- **레시피 픽스처**: 실제 빌드로 확인하려고 `samples/recipes/projects/field`를 M22에 넣었다.

| 2 | 자리를 못 찾으면 모두 실패할지, 일부는 건너뛸지 | **둘로 나눈다**(§2). 빌드와 입력에 필요한 곳은 실패, 목록·상세의 배치는 건너뛰고 `남은 일`로 알린다 |
| 3 | 필수 필드의 기본값을 `--default`로 받을지, 마이그레이션 빈칸으로 남길지 | **`--default`.** 빈칸이 없어서 명령 직후 `mvn verify`가 통과한다. 부록의 "마이그레이션 빈칸"은 쓰지 않는다 |
| 4 | `create`·`update`를 부르는 곳을 명령이 고칠지 | **고친다**(§4). `src/main`에서 넘길 값을 알 수 없으면 실패하고, 테스트에는 샘플 값을 넣는다 |
| 5 | 새 `text` 필드를 검색 조건에 넣을지 | **넣지 않는다.** 검색 대상은 업무 판단이다 |
| 6 | 마일스톤을 둘로 나눌지 | **M22, M23으로 나눈다**(§11) |

## 위험

- **이름으로 찾는다.** 타입을 풀지 않으므로, 변수 선언이 다른 파일에 있는 호출(상속한 필드 등)은 찾지 못한다. 그 호출은 컴파일 오류로 드러난다. 명령은 성공했는데 빌드가 깨질 수 있는 유일한 경우다. `다음:`에 `mvn verify`를 적는다.
- **많이 고친 crud는 실패한다.** 에이전트가 `create`의 모양을 크게 바꿨으면(행을 만드는 문이 없다) "꼭 고칠 곳"에서 걸린다. 그때는 손으로 해야 하고, 메시지가 걸린 곳을 알려야 한다.
- **crud 템플릿과 함께 바뀌어야 한다.** crud가 만드는 모양이 바뀌면 이 레시피의 자리 찾기도 바뀌어야 한다. "같은 결과" 테스트(§10)가 어긋남을 잡는다.
- **기본값이 스키마에 남는다.** `--default`의 값은 열 정의에 남는다. 앱은 늘 값을 넣으므로 동작에는 영향이 없다.
- **평가 전 설계다.** 작은 모델이 이 명령과 `남은 일`을 잘 쓰는지는 사용자의 내부 평가로 확인한다. 명령 이름과 인자는 1.2.0 릴리스 전에 확정한다.
