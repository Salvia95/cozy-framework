# ADR-0038 워크벤치 디자인 개선: 용어, 3단 구성, 구조화된 입력

- 상태: 승인 (2026-11-11, 사용자 결정). 아래 "정한 것" 여덟 가지
- 출처: 사용자 지시 "워크벤치의 디자인 개선작업을 진행하고 싶어". 현재 화면 진단과 목업은 개선안 페이지(https://claude.ai/artifact/4Y4b1M9kDfegQKcTepaqAJ)에 있다
- 이어받는 결정: [ADR-0036](0036-workbench.md) §3(엔진은 cozy-cli 하나), §4(원본은 파일), §5(안전)
- 바꾸는 결정:
  - ADR-0031 §2 화면 유형: 워크벤치에만 쓰는 유형(전체 너비 3단, 높은 밀도)을 더한다(§3).
  - ADR-0036 §1 "하지 않는 것: HTML을 직접 고치는 편집기": 프래그먼트 호출의 문자열 인자만 고칠 수 있게 한다(§7).
  - ADR-0036 M21의 범위 "키나 목록의 항목을 더하고 빼지 않는다": 목록의 행을 추가·삭제할 수 있게 한다(§7).
  - ADR-0032·0033의 `cozy recipes --json` 형식과 fragment 매니페스트 형식: 항목을 더한다(§2, §6). 이미 있는 항목은 그대로다.

- **원인은 cozy 명령의 출력을 그대로 화면에 옮긴 것이다.** 식별자가 레이블 자리에 나오고, 구조가 있는 정보가 목록과 텍스트 입력으로 표시된다.
- **1차 용어안은 반려되었다.** "바뀌는 조각", "채울 코드", "부품"처럼 풀어 쓴 조어는 쓰지 않는다. 한국어 소프트웨어에서 통용되는 표현을 쓴다(사용자 지적, 2026-11-11).

## 결정

### 1. 용어와 표기

- **한글 이름이 앞, 식별자는 뒤**다. 식별자는 소스에서 다시 찾아야 하므로 없애지 않고 고정폭 회색 글자로 붙인다(`페이지네이션 pagination`).
- **통용되는 표현을 쓴다.** 동작은 추가, 삭제, 저장, 적용, 확인, 검색, 복사 같은 일반 UI 용어로, 개발 용어는 통용 표기 그대로(프래그먼트, 컴포넌트, DTO, 이벤트 리스너, 마이그레이션) 쓴다. 새 조어를 만들지 않는다.
- **한 개념에 한 용어**다. 용어집은 [workbench.md](../conventions/workbench.md)에 둔다.
- **이름은 데이터에서 가져온다.** 템플릿에 직접 적지 않는다(§2).
- **에이전트에게 넘기는 글은 식별자로 쓴다.** "에이전트용 복사"의 `Inside:` 줄은 표시 이름이 아니라 식별자다. 형식은 바꾸지 않는다.
- 이 규칙의 범위는 워크벤치 화면이다. cozy 명령이 내는 메시지(고치는 법, 다음 할 일)는 바꾸지 않는다.

### 2. 이름의 출처

| 대상 | 출처 | 없을 때 |
| --- | --- | --- |
| 컴포넌트, 패턴, 레이아웃 | 매니페스트 항목의 `label` | 종류(컴포넌트, 프래그먼트)와 식별자 |
| 패턴이 받는 영역 | 매니페스트 파라미터의 `label` + "영역" | "영역"과 파라미터 이름 |
| 생성 항목 | `cozy recipes --json`의 `title`, `group` | (모든 레시피에 있다) |
| 상태 | 관례 이름 사전(`default`, `empty`, `noResults`, `paged`, `invalid`) | 식별자 그대로 |
| 규칙 | `cozy-rules`의 `RuleNames` | ID만 |

- **프레임워크 컴포넌트의 표시 이름은 범정부 UI/UX 디자인 시스템(KRDS)의 명칭을 참고한다.** 같은 역할의 컴포넌트나 기본 패턴이 있으면 그 명칭을 쓴다(표, 페이지네이션, 배지, 모달, 토스트, 스피너, 목록 탐색, 입력폼, 상세 정보 확인). 명칭만 참고하고 스타일과 마크업은 가져오지 않는다. 2026-11-11에 krds.go.kr의 목록에서 확인했다.

### 3. 3단 구성 (ADR-0031 개정)

- 화면 보기는 왼쪽 구조 트리, 가운데 미리보기, 오른쪽 속성 패널로 구성한다. APEX Page Designer와 Vaadin Copilot의 구성이다.
- **워크벤치용 화면 유형을 더한다.** 전체 너비, 영역마다 따로 스크롤, 높은 밀도다. 워크벤치에만 쓰고 앱 화면에는 쓰지 않는다. `design.md` §2에 적는다.
- **구조 트리**: 연결선과 접기·펼치기가 있다. 이름 앞에 종류 배지를 두지 않는다. 종류는 속성 패널에 표시한다. 패턴이 받는 영역은 중간 제목으로 표시한다.
- **속성 패널**: 왼쪽 열이 항목 이름인 표다. 읽기 전용 값은 글자, 직접 입력하는 값은 입력란, 정해진 값 중에서 고르는 값은 드롭다운이다.
- 화면 목록은 모듈별로 묶는다. 샘플 데이터는 속성 패널의 탭으로 옮겨 미리보기와 함께 본다. 소스(템플릿, 화면 명세)는 줄이 길어 가운데 칸의 탭에 둔다.

### 4. 모듈 의존성 다이어그램

- 모듈 화면은 계층형 다이어그램이다. 참조하는 모듈이 왼쪽, 참조되는 모듈이 오른쪽이다. 실선은 의존, 점선은 이벤트(발행 → 수신)다.
- 배치는 서버에서 계산해 SVG로 출력한다. 새 의존성은 없다.
- 모듈을 선택하면 의존 모듈, 참조하는 모듈, 공개 API, 화면이 속성 표로 표시된다. 모듈이 많으면 의존성 표로 전환한다.
- `cozy describe --json`은 바꾸지 않는다.

### 5. 샘플 데이터의 구조 표시

- 객체는 속성 표로, 객체의 목록은 그리드로 표시한다. 타입은 화면 명세의 `model:`이 가리키는 Java 타입에서 얻는다.
- 타입에 맞는 입력을 쓴다(boolean은 체크박스나 드롭다운, 숫자, 날짜, enum).

### 6. 코드 생성 입력의 구조화

- 반복 입력(`--field`, `--param`)은 셀에 바로 입력하는 그리드다. 단일 입력은 속성 표다.
- 앱에 있는 값(모듈, 엔티티, 이벤트, 인터페이스, DTO, 아이콘)은 드롭다운으로 선택한다.
- 변경 파일은 모듈과 계층(공개 API, 내부 구현, 화면, SQL, 화면 명세, 테스트)별 트리로 표시한다.
- **`cozy recipes --json`에 더하는 항목**: `title`, `group`, 최상위 `groups`(M24), 인자의 구성 `parts`와 선택지의 출처 `from`(M28).
- **매니페스트에 더하는 항목**: 항목과 파라미터의 `label`(M24), 파라미터의 `choices`(M29).
- **화면 명세에 더하는 항목**: `title`(M25). 화면 목록에 식별자 앞에 보인다.

### 7. 수정 기능의 확장 (ADR-0036 개정)

- **속성 패널의 매개변수 수정**: 템플릿의 프래그먼트 호출 인자 가운데 문자열 리터럴만 수정한다(`badge('고정', 'neutral')`). 표현식(`${…}`)과 선택자(`~{::#id}`)는 읽기 전용이다. cozy 명령을 거치고, 변경 파일을 확인한 뒤 적용한다.
- **샘플 데이터의 행 추가·삭제**: 목록의 행을 추가, 복제, 삭제한다. 저장 전 검증(`ScreenSpec.verify`)은 그대로다.
- 자유 배치, 색상·간격 편집, 템플릿 본문 편집은 여전히 하지 않는다.

### 8. 워드마크

- 워크벤치 머리의 표기는 필기체 워드마크 "Cozy Workbench"다. 글꼴은 Courgette다(사용자 선택).
- 글자를 SVG 경로로 변환해 템플릿에 넣는다. 글꼴 파일은 배포하지 않는다. 색은 `currentColor`다.
- Courgette는 SIL Open Font License 1.1이다. `NOTICE`에 출처를 적는다.

## 정한 것

1. 용어표와 컴포넌트 표시 이름은 개선안 페이지의 두 표를 따른다.
2. 워드마크 글꼴은 Courgette다.
3. 속성 패널의 매개변수 수정을 허용한다(문자열 리터럴 인자, cozy 명령 경유).
4. 워크벤치용 화면 유형을 디자인 원칙에 더한다.
5. 샘플 데이터의 행 추가·삭제를 허용한다.
6. recipes와 매니페스트 형식을 확장한다.
7. 새 의존성은 없다.
8. 단계는 아래 순서로 진행한다.

## M27 보완 (2026-11-12, 사용자 지시 "남은 위험 해결해줘")

- **DTO 속성의 한글 이름**: §2의 "이름은 데이터에서 가져온다"를 화면 DTO에 넓힌다. 출처는 DTO 소스의 Javadoc이다(record의 `@param`, 폼 클래스 필드의 Javadoc). 소스가 앱에 없는 프레임워크 타입(`CozyPage`)은 워크벤치가 이름을 안다. `cozy add crud`와 `cozy add field`가 필드 라벨을 Javadoc으로 남긴다.
- **샘플 데이터의 행 추가·복제·삭제**: M29에 두었던 §7의 이 기능을 M27에 넣었다. M29에는 매개변수 수정과 매니페스트 `choices`가 남는다.
- **enum과 날짜 입력**: reference-app에는 그런 화면 DTO가 없어서, 테스트 전용 DTO와 복사한 프로젝트의 화면 명세로 확인한다(`WorkbenchFixtureTest`).

## M28 (2026-11-12, 사용자 지시 "다음 작업 이어가줘")

- **`cozy recipes --json`에 더한 것**: 인자의 `parts`, `from`(§6)에 더해 `choiceLabels`(고를 값의 이름, §1의 "이름은 데이터에서"), `separator`(여럿 고르기: `--uses`, `--publish`), `strict`, 최상위 `sources`(출처 목록)를 더했다. 이미 있는 항목은 그대로다.
- **`strict`가 필요했다.** `add crud`와 `add screen`은 없는 모듈을 만든다. 모듈 칸을 있는 모듈의 드롭다운으로만 두면 새 모듈로 CRUD를 만들 수 없다. 이 두 곳은 앱의 모듈을 제안하는 글자 칸이고, 나머지 출처는 드롭다운이다.
- **아이콘은 드롭다운이 아니다.** 외곽선 아이콘이 5,233개라 이름 목록이 붙은 글자 칸으로 두고, 적은 아이콘을 칸 앞에 그린다.
- **행 버튼은 서버를 거친다.** 샘플 데이터의 그리드(M27)와 같다. 명령을 부르지 않고 행만 고친 폼을 다시 보인다.
- **변경 파일의 계층**에 §6의 여섯 가지 외에 "설정"(모듈의 `package-info.java`, `pom.xml`)을 더했다. 모듈에 딸리지 않은 파일은 "앱 공통"이다.
- 그리드의 CSS 클래스를 샘플 데이터와 함께 쓰도록 `cozy-workbench-grid`로 바꿨다.
- **입력의 테두리와 포커스**: Tabler 기본은 흰 바탕에서 체크박스 테두리 1.26:1, 포커스 2.1:1로 측정되었다. 워크벤치의 두 폼(코드 생성, 샘플 데이터)만 테두리를 secondary, 포커스를 2px primary로 바꿨다. 앱 화면의 폼은 디자인 원칙의 범위라 바꾸지 않았다.

## M29 (2026-11-12, 사용자 지시 "다음으로 넘어가줘")

- **새 명령 `cozy set arg`**: §7의 "cozy 명령을 거친다"를 따랐다. 템플릿의 뷰 이름, 줄, fragment 이름, 인자 번호, 지금 값(`--from`), 새 값으로 문자열 인자 하나를 바꾼다. 지금 값이 다르면 거절해서, 화면을 연 뒤 바뀐 템플릿을 덮어쓰지 않는다. 레시피가 아니므로 `cozy recipes`와 코드 생성 화면에는 없다.
- **매니페스트 `choices`**: 값의 목록이나 값 → 이름의 맵이다. §1의 "이름은 데이터에서"를 따라 맵에 한글 이름을 적는다. 프레임워크는 `badge` tone, `alert`·`toast` kind, `field` type에 적었다(이름은 design.md의 tone과 같은 뜻의 일반 낱말).
- **작은따옴표는 받지 않는다.** Thymeleaf가 fragment 인자의 문자열에서 `\'`를 읽지 못해 템플릿 파싱이 실패하는 것을 확인했다(3.1.5). 큰따옴표와 `&`는 문자 참조로 적어 그대로 그려진다.
- **미리보기는 다시 빌드해야 바뀐다.** 앱은 빌드 결과(`target/classes`)의 템플릿을 그린다. 구조 트리와 속성은 소스를 읽으므로 바로 바뀐다. 화면이 이 차이를 알린다.

## M30 (2026-11-12, 사용자 지시 "다음 진행해줘")

- **개요가 첫 화면이다.** 개선안의 "시작 화면 없음"을 따라 `/cozy/dev/workbench`(화면을 고르지 않은 주소)를 개요로 바꿨다. cozy 명령과 문서가 안내하는 주소가 그대로 개요로 열린다. 화면 보기는 `?spec=…`로 그대로이고, 메뉴의 "화면"은 `/cozy/dev/workbench/screens`가 첫 화면으로 넘긴다. 예전에는 주소만 열면 첫 화면이 보였다.
- **개요의 내용**은 개선안의 네 가지(규칙 위반 수, 미구현 항목, 모듈 의존성 요약, 화면 목록)다. 배치는 앱의 개요 유형(숫자 카드 줄 → 카드들)을 따르고, 폭은 다른 워크벤치 화면과 같은 전체 너비다(design.md에 더했다). 모듈 요약은 다이어그램 대신 표(의존 모듈, 참조하는 모듈)이고 다이어그램은 모듈 화면에 있다.
- **검색은 서버가 한다.** 화면을 다시 그리는 GET 폼이고 스크립트가 없어도 된다. 대상은 개선안의 화면, 컴포넌트, 생성 항목에 모듈을 더했다. 원본은 각 화면이 이미 읽는 것(화면 명세, 매니페스트, `cozy recipes`, `cozy describe`)이다. 새 형식이 없다.
- **전체 상태 보기**는 화면 보기의 `view=states`다. 상태마다 iframe으로 고른 너비의 미리보기를 그려 줄인다. 줄이는 비율은 칸 폭에 따라 `workbench.js`가 정한다(CSP가 인라인 style을 막으므로 크기는 너비별 CSS 클래스). 미리보기 안은 `inert`여서 카드 전체가 그 상태로 가는 링크 하나다.
- 개선안의 "추가 개선 사항" 가운데 나머지(소스 보기의 줄 범위, htmx 갱신, 검사의 화면별·규칙별 묶음, 트리 키보드 조작)는 이 결정의 단계에 넣지 않았다.

## 위험

- **화면 이름**: 화면 명세에 선택 항목 `title`을 더했다(M25). `cozy add crud`와 `cozy add screen`이 넣는다. 이미 있는 화면 명세에는 없으므로 식별자만 보인다.
- **앱의 매니페스트에는 `label`이 없을 수 있다.** `cozy add fragment`는 `label`을 쓰지 않는다. 없으면 종류와 식별자로 표시된다.
- **상태 이름 사전은 다섯 개뿐이다.** 관례에 없는 상태 이름은 식별자로 표시된다.
- **cozy 명령의 메시지에는 예전 낱말이 남아 있다.** 레시피 설명과 "다음 할 일"은 명령의 글이어서 "빈칸" 같은 낱말이 워크벤치에 보일 수 있다. 명령의 글과 에이전트 문서를 함께 바꿔야 하므로 이 결정의 범위에 넣지 않았다.
- **매개변수 수정은 템플릿을 고치는 새 경로다.** 범위를 문자열 리터럴로 좁히고 cozy 명령으로만 쓰게 해서, 워크벤치에만 있는 쓰기 로직이 생기지 않게 한다(M29).
