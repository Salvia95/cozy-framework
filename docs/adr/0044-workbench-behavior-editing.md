# ADR-0044 워크벤치에서 화면 안의 동작을 보고 고치기: 개발자가 터미널 없이 끝내는 흐름

- 상태: 승인 (2026-11-18, 사용자 결정 "승인할게 진행해줘"). "정할 것" 1~5는 권장안
- 출처: 사용자 요청 "지금까지의 변경 사항들이 워크벤치에 반영되어 에이전트가 아닌 개발자가 변경 사항을 확인하고 실제로 수정이 수월하게 진행될 수 있는 구조인지 확인해줘", "마일스톤으로 제시해줘"
- 이어받는 결정: [ADR-0036](0036-workbench.md) §3(엔진은 cozy-cli 하나), §4(원본은 파일), §5(안전: 쓰는 것은 cozy 명령뿐), [ADR-0038](0038-workbench-redesign.md)(3단 구성, 용어, 구조화된 입력), [ADR-0043](0043-declared-behaviors.md)(동작 명세가 원본, `cozy attach`)
- 바꾸는 결정:
  - ADR-0043 §4와 workbench.md "컴포넌트를 처음 붙이는 일(새 요소에 `x-data`)은 터미널의 `cozy attach`로 한다": 워크벤치에서도 한다(§4).
  - ADR-0036 §1의 범위: 워크벤치가 `cozy remove behavior`, `cozy rename behavior`, `cozy sync behaviors`, `cozy migrate behaviors`를 부른다(§2, §5). 부르는 길은 지금과 같은 계획 → 적용이다.
- 바꾸지 않는 것: 쓰는 것은 cozy 명령뿐이고 워크벤치는 파일을 직접 고치지 않는다(ADR-0036 §5). 같은 폼으로 적용한 것은 터미널의 같은 명령과 글자까지 같다. 동작 명세의 형식과 낱말(ADR-0043 §1), 검사 C12·C13, 의존(workbench → ui, cli. 새 라이브러리 없음)

## 배경

2.2.0의 reference-app으로 개발자 흐름을 따라가 본 결과(runtime-verifier, 1280·390px)다.

- **보는 것과 붙이는 것은 된다.** 모듈 화면의 "화면 안의 동작", 구조 트리의 `동작 N`, 속성 표의 요소별 바인딩과 펼친 명세, 쓸 수 있는 이름 안내, `cozy attach`의 계획 → 적용, 없는 이름의 거절(있는 이름 목록)이 동작한다. 가로 넘침, 콘솔 오류, CSP 위반은 없다.
- **명세와 만든 JS를 볼 수 없다.** 소스 보기는 화면 템플릿과 화면 명세뿐이다. `behaviors/{모듈}.yml`, `static/{모듈}/{모듈}.js`, 붙인 자리가 있는 fragment 템플릿(`memo/internal/fields.html`)은 열 수 없고, 속성 표의 `fields.html:7`은 링크가 아니다.
- **컴포넌트를 고치는 폼이 지금 내용을 모른다.** 코드 생성의 "화면 동작"에 이미 있는 `memo`·`body-count`를 넣어도 상태·계산·동작 칸이 비어 있다. 항목을 지우거나(`cozy remove behavior`) 이름을 바꾸는(`cozy rename behavior`) 길은 워크벤치에 없다.
- **낱말을 알려 주는 곳이 없다.** `gt`, `format`, `set`, `within` 같은 함수와 단계는 `ui.md`에만 있다. 폼은 칸마다 예시 한 줄이다. 개발자가 식을 처음부터 쓰기 어렵다.
- **확인 화면에 바뀌는 글이 없다.** "변경 파일 확인"은 파일 목록과 한 줄 요약(`계산 under`, `붙임 x-show="over"`)이다. 앞뒤 비교가 없다.
- **적용해도 미리보기에 바로 보이지 않는다.** 실행 중인 앱은 빌드 결과(`target/classes`)의 템플릿과 `static/`을 읽는다(`CozyModuleScripts`는 `classpath*:static/*/*.js`). 동작을 조금 고칠 때마다 다시 빌드하고 실행해야 한다.
- **터미널로 나가야 하는 일이 있고, 화면은 그 명령을 알려 주지 않는다.** 새 요소에 컴포넌트를 붙이기, 동작 지우기·이름 바꾸기, `cozy sync behaviors`(C12), `cozy migrate behaviors`(C12 경고). C13 항목은 `command`가 비어 "직접 수정"으로 보인다.
- **검색이 동작을 찾지 못한다.** `memoBodyCount`나 목적의 글자("글자 수")로 찾으면 결과가 없다.
- **문구가 맞지 않는 곳**: 이미 붙인 컴포넌트를 고쳐도 확인 화면이 "붙이기 전에는 cozy check가 C13으로 실패합니다"라고 한다. 명세와 JS가 "앱 공통 › 설정" 묶음에 들어간다. `cozy attach`의 오류가 "'lable'가"처럼 조사를 고르지 않는다. `동작 N`의 N(요소 수)을 화면이 설명하지 않는다.

## 결정

### 1. 동작의 소스를 본다

- 화면 보기의 소스 탭에 "동작 명세"(`behaviors/{모듈}.yml`)와 "만든 JS"(`static/{모듈}/{모듈}.js`, 읽기 전용이고 "cozy가 만든 파일" 표시)를 더한다. 화면이 쓰는 모듈 컴포넌트가 없으면 탭이 없다.
- 속성 표의 요소 위치(`templates/…:줄`)는 그 템플릿의 소스 보기 그 줄로 가는 링크다. 넣은 fragment의 템플릿도 열린다.
- 모듈 화면의 컴포넌트마다 명세 소스와 만든 JS로 가는 링크를 둔다.

### 2. 컴포넌트를 고치는 폼

- 모듈 화면과 속성 표의 컴포넌트에 **고치기**를 둔다. "화면 동작" 폼을 그 컴포넌트의 지금 항목(목적, 상태, 계산, 동작, 받는 화면 이벤트)으로 채워 연다. 엔진은 `cozy describe --json`의 `modules[].behaviors[]`를 읽는다.
- 채운 행을 바꾸거나 더한 것은 `cozy add behavior`(같은 이름이면 그 항목을 고친다)다. 행을 지운 것은 같은 계획 안의 `cozy remove behavior … --state 이름`이다. 계획은 두 명령을 차례로 보이고, 적용은 둘 다 성공해야 한다(앞의 것이 실패하면 뒤의 것을 부르지 않는다). 지운 항목을 템플릿이 부르면 `remove`가 거절하고, 그 이유를 그대로 보인다.
- **컴포넌트 지우기**와 **이름 바꾸기**는 같은 화면의 따로 된 동작이다(확인 창 → 계획 → 적용). 명령은 `cozy remove behavior`, `cozy rename behavior`다.

### 3. 낱말 안내

- `cozy recipes --json`의 `behavior`에 `vocabulary`를 더한다: 계산 함수, 동작 단계, 이벤트 값, 상태의 종류마다 이름, 모양(`gt(a, b)`), 한 줄 설명. 원본은 JS를 만드는 코드의 목록 하나이고, `ui.md`의 표와 같은지 테스트가 본다.
- 폼의 계산·동작 칸 옆에 접고 펴는 낱말 표를 두고, 칸은 그 컴포넌트의 이름과 낱말을 제안한다(`datalist`). 붙이기 폼의 이름 칸도 글자 칸 대신 쓸 수 있는 이름의 선택 칸이다.
- `cozy attach`와 `cozy add behavior`의 "없는 이름" 오류는 가까운 이름을 하나 제안한다("`label`인가요?"). 조사는 받침에 맞춘다.

### 4. 새 요소에 붙이기

- 속성 표에서 컴포넌트가 없는 요소(앱 템플릿, 여는 태그가 그 줄에 하나)에 **컴포넌트 붙이기**를 둔다. 앱 컴포넌트와 `cozy` 컴포넌트를 고르고, 그 컴포넌트가 읽는 `data-*`(명세의 `@data-*`, 프레임워크 명세의 `data`)를 칸으로 받는다. 명령은 `cozy attach <컴포넌트> --at <템플릿>:<줄> --data …`이다.
- `cozy attach`가 거절하는 곳(그려질 때 바뀌는 요소, 이미 다른 컴포넌트가 붙은 요소)은 이유를 그대로 보인다.

### 5. 바뀌는 글과 바로 보기

- **앞뒤 비교**: 계획(`--dry-run --json`)이 바뀌는 파일마다 바뀐 뒤의 글을 돌려준다(한 파일 256KB까지, 넘으면 비교 없이 목록만). 워크벤치가 지금 파일과 줄 단위로 비교해 바뀐 줄과 앞뒤 세 줄을 보인다. 비교는 cozy-cli 안의 짧은 코드로 하고 라이브러리를 더하지 않는다. 동작 명세와 만든 JS도 같다.
- **바로 보기**: 워크벤치가 켜진 dev 실행에서 앱의 템플릿과 `static/`을 소스 폴더(`src/main/resources`)에서 먼저 읽는다. 적용 뒤 새로고침만으로 미리보기와 화면에 보인다. Java와 SQL은 지금처럼 다시 빌드해야 하고, 확인 화면은 무엇이 바로 보이고 무엇이 빌드가 필요한지 나눠 알린다. 배포 패키지(`-Pdist`)와 테스트는 빌드 결과만 읽는다.

### 6. 검사에서 바로 고치기

- 검사 화면과 개요의 C12는 `cozy sync behaviors`, C12 경고는 `cozy migrate behaviors`의 **계획** 버튼을 둔다. 옮기기의 "남은 일"(`파일:줄`, 무엇이 낱말 밖인지)은 계획 화면에 그대로 보인다.
- C13 항목은 종류에 맞는 화면으로 간다: 붙이지 않은 컴포넌트 → 그 모듈의 화면 목록과 §4, 부르지 않는 동작 → 컴포넌트의 붙인 곳, 받거나 내는 곳이 없는 화면 이벤트 → §2의 고치기(받는 화면 이벤트)와 모듈 화면의 화면 이벤트.
- 검색이 컴포넌트 이름, 목적, 화면 이벤트를 찾는다.

## 이번에 하지 않는 것

- 동작 명세를 글자로 고치는 편집기. 명세는 폼과 명령으로만 바뀐다(손으로 고치면 `cozy sync behaviors`).
- htmx 속성을 붙이고 고치기(ADR-0043 정할 것 5).
- 화면 명세의 상태에 Alpine 상태를 적어 미리보기를 그 상태로 그리기.
- Java와 SQL을 바로 보이기(다시 빌드).

## 위험

- **소스에서 읽는 dev와 빌드 결과가 다를 수 있다.** 개발자가 본 화면과 `mvn verify`의 렌더링 검사가 다른 파일을 볼 수 있다. dev에서만 켜고, 검사와 배포는 빌드 결과만 읽으며, 끄는 설정을 둔다. 템플릿 캐시를 끄므로 dev 화면이 조금 느려진다.
- **두 명령의 한 계획은 반쯤 적용될 수 있다.** 뒤의 명령이 적용 중에 실패하면 앞의 것은 남는다. 계획 단계에서 두 명령을 모두 `--dry-run`해 거절을 먼저 보이고, 적용 순서를 지우기 → 더하기로 해 남는 상태도 명세로서 맞게 한다.
- **채워진 폼이 오래된 내용일 수 있다.** 폼을 연 뒤 다른 곳에서 명세가 바뀌면 덮어쓴다. 폼에 명세의 해시를 넣고, 적용할 때 다르면 다시 열라고 한다(화면 명세의 샘플 데이터 수정과 같은 방식).
- **바뀐 뒤의 글이 응답을 키운다.** 파일당 256KB까지만 보내고, 넘으면 목록만 보인다.

## M51 (2026-11-18, 사용자 지시 "승인할게 진행해줘")

- **시작할 때 확인한 최신 GA**: 릴리스 2.2.0의 확인과 같다. 미뤄 둔 Tabler Icons 3.52.0(외곽선 5,490개, 채운 1,054개)으로 올렸다. 빠진 아이콘은 `align-justified` 하나이고 레포는 쓰지 않는다(ADR-0017).
- **소스 보기**
  - 화면 보기의 가운데 탭에 `동작 명세`(`view=behavior`)와 `만든 JS`(`view=script`)를 더했다. 화면이 앱 컴포넌트를 쓸 때만 보이고, 모듈이 둘 이상이면 `module`로 고른다. 소스 위에 고치는 길을 한 줄로 알린다.
