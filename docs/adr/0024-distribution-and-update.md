# ADR-0024 배포 장치: 패키징 도구, AOT 캐시, 교체 스크립트, 롤백

- 상태: 승인 (2026-11-06)
- 출처: M6 구현 (PRD §9.2, §9.4~9.6). ADR-0001(jpackage), ADR-0010(데이터 분리), ADR-0012(자체 업데이트)를 구체화한다.

## 결정

### 1. 패키징은 Java 코드(`CozyPackager`)로 하고, cozy-parent의 dist 프로필이 exec:exec로 부른다

- **위치**: `CozyPackager`는 cozy-starter-runtime의 internal 패키지에 둔다.
- **실행 방식**: dist 프로필이 앱의 런타임 클래스패스로 별도 JVM을 띄워 실행한다.
- **하는 일**: 앱의 `application.yml`에서 `cozy.app.id`를 읽어, jar 풀기, jpackage(ToolProvider), 훈련 실행, zip, SHA-256, 매니페스트까지 한 번에 한다.
- **근거**:
  - bash와 PowerShell 스크립트를 따로 두면 Windows와 Linux의 동작이 갈라진다.
  - Java 코드는 테스트할 수 있다.
  - 새 Maven 플러그인 없이 ADR-0017 표의 exec-maven-plugin만 쓴다.
- **플러그인 순서**: 부모 프로필의 플러그인은 앱 POM의 플러그인보다 앞에 놓인다. 그래서 프로필 안에서 spring-boot-maven-plugin을 exec보다 먼저 선언해 repackage가 먼저 돌게 한다.
- **앱이 아닌 모듈**: dist 프로필의 enforcer가 `src/main/resources/application.yml`이 없는 모듈에서 빌드를 멈춘다.

### 2. AOT 캐시는 풀린 jar와 두 단계 훈련으로 만든다

- **jar 풀기**: Boot의 중첩 jar는 AOT 캐시 대상이 아니다. 그래서 `-Djarmode=tools extract`로 풀어 jpackage의 입력으로 쓴다.
- **두 단계 훈련**: jpackage 런타임에는 `bin/java`가 없다. 그래서 JDK 25의 한 단계 방식(`-XX:AOTCacheOutput`)은 캐시를 조립하는 자식 JVM을 띄우지 못한다(확인함). 대신 생성된 런처로 두 단계를 실행한다.
  1. `AOTMode=record`: 훈련 실행
  2. `AOTMode=create`: 캐시 생성
  - 옵션은 런처 cfg의 `[JavaOptions]`를 잠시 바꿔 넣는다.
- **훈련 실행**: `cozy.runtime.training=true`면 기동 뒤 `/`와 패턴 카탈로그를 요청하고 종료한다. 하나라도 실패하면 패키징이 실패한다.
- **효과**: reference-app 기동이 5.2초에서 2.2초로 줄었다.
- **파일 시각**: AOT 캐시는 jar의 수정 시각을 초 단위로 대조하고, zip은 시각을 2초 단위로 담는다. 그래서 다음 두 가지를 한다.
  - 훈련 전에 실행 폴더의 모든 파일 시각을 짝수 초로 맞춘다.
  - zip을 만들고 풀 때 시각을 보존한다.
  - 이렇게 하지 않으면 설치·업데이트한 앱에서 캐시가 매번 버려졌다(종단 검증에서 발견).
- **캐시가 맞지 않을 때**: 캐시가 망가지거나 없어도 JVM은 경고만 남기고 정상 기동한다. 이를 확인했고, 종단 검증이 매번 다시 확인한다.

### 3. 새 버전은 앱 폴더 옆(`{폴더}.new`)에 풀고, 교체는 이름 바꾸기로 한다

- **풀 위치**: `{dataDir}/update/`에 풀면 앱 폴더와 볼륨이 다를 수 있다. 그러면 이동이 복사가 되어 느리고, 중간에 실패할 수 있다. 그래서 앱 폴더 옆에 푼다.
- **보관하는 폴더**:
  - 이전 폴더 `{폴더}.old`는 다음 업데이트 전까지 남긴다(수동 복구용).
  - 실패한 새 폴더는 `{폴더}.failed`로 옮긴다.
- **zip 형식**: zip은 최상위 폴더 하나만 허용한다. 풀 위치 밖을 가리키는 항목이 있으면 아무것도 풀지 않는다. Linux 실행 권한은 zipfs의 POSIX 속성으로 보존한다.

### 4. 교체 스크립트는 앱과 분리해 실행하고, 시작을 확인한 뒤에 앱을 끝낸다

- **스크립트 형식**: Windows는 PowerShell 5.1이다. 프로세스 ID로 기다리기와 종료가 필요해서 .cmd 대신 골랐다. Linux는 bash이고, 개발과 종단 검증용이다.
- **Windows 실행 방식**: 스크립트를 WMI `Win32_Process.Create`로 실행한다.
  - 앱 프로세스가 작업 개체(Job)에 속해 있으면 자식 프로세스가 함께 끝날 수 있다. WMI로 만든 프로세스는 그 밖에서 돈다.
  - WMI로 만든 프로세스는 환경 변수를 물려받지 않는다. 그래서 스크립트가 `COZY_DATA_DIR`을 직접 설정한다.
  - 스크립트 파일은 UTF-8 BOM으로 쓴다. Windows PowerShell 5.1은 BOM이 없으면 시스템 코드 페이지로 읽는다.
- **런처 환경 변수**: jpackage 런처는 자기 프로세스에 `_JPACKAGE_LAUNCHER`를 넣는다.
  - 이것을 물려받은 새 런처는 cfg를 읽지 않고 종료 코드 1로 끝난다(Linux에서 확인, 종단 검증에서 발견).
  - 그래서 앱은 스크립트에 `_JPACKAGE*` 변수를 넘기지 않는다. 스크립트도 새 버전을 실행하기 전에 지운다.
- **시작 확인**: 스크립트는 시작하자마자 `script-started`를 쓴다. 앱은 이것을 20초 안에 확인해야 종료한다.
  - 확인하지 못하면 `cancelled`를 남기고 종료하지 않는다(실행 정책으로 막힌 경우 등).
  - 늦게 뜬 스크립트는 `cancelled`를 보고 아무것도 하지 않는다.
- **Windows에서 확인한 것**: WSL 상호 운용으로 실제 Windows PowerShell에서 성공과 롤백 두 경로를 돌려 확인했다.
  - 가짜 앱을 썼다.
  - 경로에 한글과 공백을 넣었다.
  - 스크립트는 WMI로 실행했다.

### 5. 성공 판단은 새 앱의 준비 신호(버전)로 하고, 롤백은 폴더와 데이터를 함께 되돌린다

- **준비 신호**: 새 앱은 기동을 마치면 `update/ready`에 자기 버전을 쓴다. Flyway 마이그레이션과 컨텍스트 기동이 끝난 뒤다.
  - 스크립트는 버전이 맞는 신호만 성공으로 본다. 그래서 이전 실행이 남긴 파일로 착각하지 않는다.
  - 새 프로세스가 신호 없이 먼저 끝나면 시간을 기다리지 않고 바로 되돌린다.
- **데이터 백업**: 교체 직전에 `{dataDir}/data`를 `update/data-backup`에 복사하고, 롤백하면 이것으로 바꾼다.
  - 실패한 새 버전이 일부 바꾼 DB를 이전 버전이 읽지 않게 하기 위해서다.
  - 새 버전은 준비 신호 전에 실패했으므로 사용자 데이터가 쓰이지 않았다.
- **실패한 버전**: `update/failed-version`에 남기고 다시 권하지 않는다. 더 새 버전은 권한다.
- **결과 알림**: 결과(`result.properties`)는 새 앱이 준비된 뒤에 쓰인다. 그래서 앱은 기동할 때가 아니라 화면이 물어볼 때 파일을 확인한다.

### 6. 종료는 JVM까지 끝낸다

- **이유**: 화면 메뉴, 트레이, 업데이트로 종료하면 `SpringApplication.exit` 뒤에 `System.exit`까지 한다. 트레이(AWT) 스레드가 남아 프로세스가 살아 있으면 스크립트가 앱 폴더를 옮길 수 없기 때문이다.
- **켜는 쪽**: 이 동작은 `CozyApplication.run`이 켜는 `cozy.runtime.exit-jvm`으로 한정한다. 테스트 컨텍스트에서는 꺼져 있다.

### 7. 진단 파일의 비밀 가리기와 확장점

- **설정 요약**: 앱 설정 출처만 넣는다. 시스템 환경 변수와 시스템 속성은 넣지 않는다.
- **비밀 값 가리기**:
  - 비밀로 보이는 키의 값을 가린다.
  - 주소 안의 사용자 정보를 가린다.
  - `-D` JVM 인수도 같은 규칙으로 가린다.
- **확장점**: `CozyDiagnosticsContributor`(공개 API)로 스타터와 앱이 파일을 더한다.
  - sqlite 스타터는 PRAGMA와 Flyway 이력을 더한다.
  - events 스타터는 미완료 이벤트 개수를 더한다. 이벤트 내용은 넣지 않는다.

### 8. 종단 검증은 e2e 프로필의 별도 모듈로 둔다

- **검증 내용**: `samples/dist-e2e`가 reference-app 사본을 세 버전으로 실제 패키징한다. 그다음 설치, 업데이트, 롤백, 종료를 검증한다. 이것이 M6 완료 기준이다.
- **실행 시점**: jpackage와 훈련 실행으로 몇 분 걸려 기본 `mvn verify`에는 넣지 않는다. `mvn -Pe2e install`로 돌린다.
- **빠른 검증**: 스크립트의 교체·롤백·취소 논리는 가짜 app-image로 기본 빌드(`UpdateServiceTest`)에서도 매번 검증한다.

## 결과

- 새 의존성과 플러그인은 없다. jpackage는 JDK 25에 들어 있다.
- 업데이트 설치는 요청 스레드에서 내려받기를 끝낸 뒤 응답한다. 큰 패키지를 느린 공유 폴더에서 받으면 버튼을 누른 뒤 한동안 기다린다. 진행 표시는 v1 범위 밖이다.
- PowerShell 스크립트가 그룹 정책으로 막힌 PC에서는 업데이트를 설치할 수 없다. 앱은 계속 동작하고 이유를 알린다. 사내 정책 확인은 PRD §13의 미결 항목(앱 설치 위치)과 함께 본다.
