# ADR-0023 이벤트 실행 구성: 인박스 위치, 실행기, 보관, 호환 검사

- 상태: 승인 (2026-11-06)
- 출처: M5 구현 (PRD §8). ADR-0006(저장소 직접 구현)과 ADR-0018(직렬화 분리)을 보완한다.

## 결정

### 1. 인박스는 리스너 트랜잭션 안쪽에서 실행되도록 어드바이저 순서를 고정한다

- **문제**: Spring의 트랜잭션 어드바이저는 기본 순서가 `LOWEST_PRECEDENCE`다. 같은 순서의 어드바이저끼리는 실행 순서가 정해져 있지 않다. 인박스 행을 넣는 일이 리스너 트랜잭션 밖에서 돌면 다음 문제가 생긴다.
  - 인박스 행이 따로 커밋된다.
  - 리스너가 실패해도 인박스 행이 남는다.
  - 다시 실행할 때 본문을 건너뛴다. 즉 이벤트를 잃는다.
- **결정**: 어드바이저 순서를 다음과 같이 고정한다.
  - **트랜잭션 어드바이저**: cozy-starter-events가 `@EnableTransactionManagement(order = LOWEST_PRECEDENCE - 1000)`을 선언한다. Boot의 기본 트랜잭션 설정은 이것이 있으면 물러난다.
  - **인박스 어드바이저**: `LOWEST_PRECEDENCE`이므로 트랜잭션 어드바이저보다 안쪽이다.
  - **결과 순서**: 비동기 → Modulith 완료 기록(`HIGHEST_PRECEDENCE + 10`) → 트랜잭션 → 인박스 → 본문
- **실패로 닫기**: 인박스는 실행 중인 트랜잭션이 없으면 예외를 던진다.
- **검증**: 인박스 순서를 바깥으로 바꾸면 계약 테스트 5개가 실패한다(M5에서 확인).
- Modulith의 완료 기록은 리스너 트랜잭션 밖에서 따로 커밋된다. 그래서 "본문 커밋 뒤, 완료 기록 전 종료"라는 틈이 생기고, 인박스가 이 틈을 막는다.

### 2. 비동기 실행기는 앱 전체 실행기를 동시 2개로 둔다

- `@ApplicationModuleListener`는 `@Async`라서 Boot의 `applicationTaskExecutor`를 쓴다. 별도 실행기를 만들지 않고 `spring.task.execution.pool.core-size`와 `max-size`의 기본값을 2로 둔다.
- 앱의 다른 `@Async`도 이 실행기를 함께 쓴다. 로컬 도구의 비동기 작업은 대부분 SQLite 쓰기를 하므로, 같은 제한이 맞다.

### 3. 완료 처리는 UPDATE만 지원하고, 보관 기간이 지나면 정리 작업이 지운다

- Modulith의 `completion-mode`(UPDATE, DELETE, ARCHIVE) 중 UPDATE만 구현한다. 다른 값을 설정하면 기동이 실패한다.
- `EventRetentionCleaner`가 보관 기간(`cozy.events.retention`, 기본 30일)이 지난 행을 지운다. 대상은 완료 발행 기록과 인박스 행이다.
- 실행 시점은 기동 1분 뒤, 그 뒤로는 `cozy.events.cleanup-interval`(기본 6시간)마다다. `@EnableScheduling`에 기대지 않고 자기 스케줄러를 쓴다. 앱의 스케줄링 설정과 섞이지 않게 하기 위해서다.
- 미완료 발행 기록이 있는 이벤트의 인박스 행은 지우지 않는다. 그 이벤트는 아직 다시 전달될 수 있기 때문이다.

### 4. 저장소는 인터페이스의 모든 메서드를 직접 구현하고, 테스트가 이것을 강제한다

- 계약 테스트가 `EventPublicationRepository`의 모든 인스턴스 메서드를 `SqliteEventPublicationRepository`가 직접 선언했는지 반사로 검사한다.
- 이유: Modulith를 올렸을 때 새 메서드가 기본 구현(아무 일도 하지 않음)에 맡겨지면 조용히 틀린다. 이 검사가 그것을 빌드 실패로 바꾼다(PRD §8.5 "인터페이스 변경 감지").

### 5. 이벤트 호환 검사(C6)는 버전별 샘플을 현재 클래스와 대조한다

- 이벤트 전용 매퍼(`CozyEventMapper`)는 다음과 같이 설정한다. 그래서 역직렬화가 성공하는 것만으로는 필드 삭제나 이름 변경을 잡지 못한다.
  - 모르는 필드를 무시한다.
  - 없는 primitive를 0과 false로 채운다.
- 그래서 C6는 다음을 확인한다. 숫자는 노드 종류(int, long)와 상관없이 값으로 비교한다.
  1. 샘플을 현재 클래스로 읽었다가 다시 쓴다. 샘플의 모든 필드가 같은 값으로 남아 있는지 확인한다.
  2. 가장 높은 버전 샘플이 현재 클래스의 모든 필드를 가지는지 확인한다.
- 샘플 폴더 이름은 클래스 단순 이름이다. 짝이 없는 폴더는 클래스 이름 변경으로 보고 실패시킨다.
- 직렬화 결과를 정렬된 속성 순서로 고정했다. 발행 기록은 `serialized_event` 문자열로 찾으므로 같은 이벤트는 늘 같은 문자열이어야 한다.

### 6. 강제 종료 시나리오는 실제 프로세스로 검증한다

- 계약 테스트가 테스트 앱을 별도 JVM으로 띄운다. 이벤트를 발행하고, 리스너 본문이 멈춰 있는 동안 `destroyForcibly`로 종료한다.
- 같은 데이터 경로로 다시 띄우면 이벤트가 처리된다. 본문의 쓰기는 정확히 한 번 남는다. 종료 전의 쓰기는 커밋되지 않았기 때문이다.

## 결과

- 새 의존성은 `spring-modulith-events-core`(Modulith BOM, Apache-2.0)뿐이다. Modulith의 JDBC 저장소와 Jackson 직렬화 모듈은 쓰지 않는다.
- 모듈 공개 fragment는 다음 위치에 둔다.
  - 템플릿: `templates/{모듈}/api/`
  - 매니페스트: 앱 매니페스트
  - 패턴 카탈로그: `api` 묶음으로 보인다
- 앱이 `@EnableTransactionManagement`를 직접 선언하면 어드바이저 순서가 바뀔 수 있다. 이 경우 리스너가 명확한 메시지로 실패한다. 이 내용을 events.md에 적었다.
