# ADR-0036 워크벤치: 앱 안에서 화면을 보고, 가리키고, cozy 명령으로 만든다

- 상태: 승인 (2026-11-10, 사용자 "승인할게 바로 진행해줘"). 방향은 사용자 결정이다: "워크벤치로 간다", "파일을 쓰는 명령 폼까지 한 번에 계획", "dev 전용 모듈", "core가 아닌 cli이니 동일 cli를 공유", "IntelliJ는 소스 수정에만 쓰고 UI 작업은 워크벤치를 따로 본다"
- 바꾸는 결정: ADR-0016(모듈 의존 방향에 `workbench → ui, cli` 추가). ADR-0001~0015는 바꾸지 않는다
- 조사: 2026-11-10의 UI 빌더 방향 조사(시중·오픈소스 도구 20여 개). 요약은 아래 "배경"에 있다

## 배경

- **빌릴 완제품이 없다.** htmx + Thymeleaf를 캔버스에서 다루는 빌더는 찾지 못했다. 자유 캔버스 편집기(GrapesJS 등)는 자기 JSON 모델이 원본이고 HTML은 한 방향 내보내기라서, 손으로 쓴 템플릿을 다시 읽어 고치지 못한다.
- **서버 렌더링 진영에서 살아남은 형태는 "실행 중인 앱 안의 미리보기"다**(Lookbook, phoenix_storybook, Thymeleaflet). Cozy의 패턴 카탈로그(`/cozy/dev/catalog`)와 화면 스펙이 이미 그 형태다.
- **IDE 비주얼 디자이너는 유지비가 크다.** Vaadin Designer는 IntelliJ 플러그인 API 변경으로 두 번 깨졌다는 Vaadin 측 답변이 있고 V25부터 deprecated다.
- **Cozy에는 구조를 만드는 엔진이 이미 있다.** cozy-cli가 계획을 세우고 원자적으로 적용한다(ADR-0032, ADR-0033). 에이전트가 이 명령을 쓴다.

## 결정

### 1. 형태

- 앱의 dev 서버 안에서 도는 브라우저 도구다. 주소는 `/cozy/dev/workbench`다.
- 화면은 Thymeleaf + htmx + Tabler로 만든다. 새 라이브러리를 들이지 않는다(ADR-0017 표는 그대로다).
- IDE 연동은 넣지 않는다. 소스 위치는 `파일:줄` 글자로 보이고 복사할 수 있게만 한다. 에디터를 띄우지 않는다.
- 하지 않는 것: 자유 배치, 색·간격 편집, HTML을 직접 고치는 편집기. 디자인 원칙(ADR-0031)과 규칙 R1~R15를 우회하는 길을 만들지 않는다.

### 2. 새 모듈 `cozy-workbench` (ADR-0016 개정)

- dev 전용 모듈이다. `cozy-parent`를 상속하고 `cozy-ui`와 `cozy-cli`에 의존한다.
- 의존 방향: `workbench → ui, cli`. `ui`와 `cli`는 워크벤치를 모른다. 패턴 카탈로그와 스펙 미리보기 경로는 `cozy-ui`에 그대로 둔다(렌더링 검사가 쓴다).
- 앱은 `cozy-workbench`를 의존으로 가진다. 앱 코드는 이 모듈의 타입을 쓰지 않는다(자동 설정만).
- **배포 패키지에는 넣지 않는다.** `cozy-parent`의 repackage 설정이 `cozy-workbench`와 `cozy-cli`를 뺀다. `-Pdist` 픽스처가 패키지에 두 jar가 없는지 본다.
- **켜지는 조건**: dev 프로필이고 `cozy.dev.workbench.enabled`가 꺼져 있지 않을 때. 카탈로그와 같은 방식이다.
- 넣는 길: 아키타입이 새 앱의 pom에 넣는다. 이미 있는 앱은 `cozy enable workbench`로 넣는다.

### 3. 엔진은 cozy-cli 하나를 공유한다

- 워크벤치는 에이전트가 쓰는 것과 **같은 버전의 cozy-cli**를 같은 프로세스에서 부른다(`CozyCli.run(...)`과 `--json`). 다른 판을 고정해 두지 않는다.
- **워크벤치는 cozy 명령의 화면이다.** 보이는 것은 `describe`, `check`, `recipes`의 `--json`이고, 만드는 것은 `add`·`link`·`enable`의 계획(`--dry-run --json`)과 적용이다. 워크벤치가 따로 생성하거나 고치는 코드를 갖지 않는다.
- 워크벤치에 필요한 정보가 명령에 없으면 **명령에 더한다.** 예: 화면 하나의 구조(패턴, 슬롯, fragment 참조와 줄 번호)는 `describe`에 더한다. 그러면 에이전트도 같은 정보를 받는다.
- `--json` 출력이 워크벤치와 cli 사이의 계약이다. 형식은 `docs/conventions/cli.md`에 있고, 워크벤치 테스트가 reference-app으로 확인한다.
- cozy-cli는 javac 파서를 쓰므로 dev 실행에는 JDK가 필요하다. 앱 사용자 PC(배포 패키지)에는 영향이 없다.

### 4. 원본은 파일이다

- 워크벤치는 자기 모델이나 저장소를 갖지 않는다. 읽는 것도 쓰는 것도 앱의 템플릿, 스펙 YAML, 매니페스트, Java 소스다.
- **직접 쓰는 파일은 하나뿐이다**: 화면 스펙 YAML의 상태별 fixture 값(§6의 다섯째 단계). 그 밖의 모든 쓰기는 cozy 명령이 한다.
- **소스 폴더에서 실행할 때만 쓴다.** 앱 프로젝트(`pom.xml`과 `src/main/java`)를 찾지 못하면(jar나 app-image로 실행) 쓰기 기능을 끄고 이유를 보인다.
- **바뀐 것이 보이는 때**: 템플릿과 스펙은 dev에서 소스 폴더(`src/main/resources`)를 먼저 읽어 바로 보인다. Java가 바뀌는 명령(컨트롤러, DTO 등)은 적용한 뒤 "다시 빌드하고 실행해야 보입니다"를 알린다. 자동 재시작 도구는 들이지 않는다.

### 5. 안전

- dev 프로필에서만 등록한다. 127.0.0.1 바인딩과 Host 필터(런타임 기본)가 그대로 적용된다.
- 파일을 쓰는 요청은 POST이고 CSRF 토큰(런타임 기본)을 지난다. 여기에 `Origin`이 자기 주소인지 확인한다.
- 쓰는 경로는 cozy-cli의 `Plan`이 정한다(프로젝트 폴더 기준 상대 경로). 워크벤치는 경로를 입력받지 않는다. 스펙 저장은 `src/main/resources/specs/` 아래의 이미 있는 파일만 받는다.
- 명령의 인자는 폼의 값으로만 만든다. 셸을 거치지 않는다(같은 프로세스에서 인자 배열로 부른다).

### 6. 단계

| 마일스톤 | 내용 | 완료 기준 |
| --- | --- | --- |
| M17 모듈과 보기 | `cozy-workbench` 모듈, `/cozy/dev/workbench`: 화면 목록, 화면의 구조 트리(패턴 슬롯 → fragment), 상태 탭, 뷰포트 전환, 템플릿·스펙 소스 보기. `describe`에 화면 구조를 더한다. `cozy enable workbench`, 아키타입, 배포 패키지 제외. Tabler 1.7.4와 Tabler Icons 3.51.0으로 올린다 | reference-app의 모든 화면과 상태가 보인다. dev가 아니면 404다. `-Pdist` 패키지에 `cozy-workbench`, `cozy-cli`가 없다 |
| M18 가리키기 | 미리보기의 요소를 누르면 그 요소의 `파일:줄`, fragment, 스펙 상태를 보인다. "에이전트용 복사"가 위치와 플레이북 이름을 담은 글을 만든다. 트리와 미리보기의 선택이 서로 따라간다 | 워크벤치 미리보기 밖의 HTML(운영, 렌더링 검사)은 한 글자도 달라지지 않는다 |
| M19 검사와 지도 | `cozy check` 결과를 화면별로 보이고, 위반의 `고치는 명령`을 보인다. 앱의 지도(모듈, 의존, 이벤트, 빈칸)를 `describe`로 보인다 | 위반 픽스처의 위반이 워크벤치에 같은 문구로 보인다 |
| M20 명령 폼 | `recipes --json`으로 폼을 만든다(`add screen`·`crud`·`fragment`부터, 나머지 레시피도 같은 방식). 폼 → 명령 글자 → 계획(`만듦`·`바꿈`) → 적용 → 남은 빈칸 | 폼으로 만든 결과가 같은 명령을 터미널에서 실행한 것과 바이트 단위로 같다. 소스 폴더가 아니면 적용이 꺼진다 |
| M21 fixture 편집 | 속성 패널에서 스펙 YAML의 상태 값을 고치고 저장한다. 상태 추가·복제 | 저장한 스펙으로 렌더링 검사(C3~C5)가 통과한다. 주석과 키 순서가 보존된다 |

- 화면이 바뀌는 마일스톤마다 runtime-verifier로 실제 화면을 확인한다(ADR-0030). 워크벤치 자신의 화면도 `design.md`를 따른다.
- 워크벤치가 끝나면 Windows 확인을 한 번에 한다(1.0.0과 1.1.0에서 미룬 항목 포함).

### 7. 기존 도구에서 가져오는 것

| 가져오는 것 | 어디서 | Cozy에서는 |
| --- | --- | --- |
| 트리 · 미리보기 · 속성의 선택 연동 | Oracle APEX Page Designer | 패턴 슬롯이 트리의 제목, fragment가 잎 |
| 고정 팔레트 | Puck | 매니페스트가 팔레트다. 자유 편집이 없다 |
| 좁은 대상에만 쓰기 | Storybook "save from controls" | 직접 쓰는 것은 스펙의 fixture뿐 |
| 브라우저는 모델, 생성은 CLI | JHipster JDL Studio | 폼이 cozy 명령을 만들고 cozy-cli가 생성 |
| 요소에서 소스로 | LocatorJS | dev 미리보기에서만 요소에 템플릿 위치를 싣는다 |
| 요소를 골라 에이전트에 넘기기 | Stagewise, VS Code 통합 브라우저 | `파일:줄`, fragment, 플레이북을 묶어 복사 |

## 결과

- 사람과 에이전트가 같은 명령으로 구조를 만든다. 워크벤치에서 만든 것과 터미널에서 만든 것이 같다.
- cozy-cli가 라이브러리로도 쓰인다. `CozyCli.run`과 `--json` 형식이 공개 API가 된다.
- cozy-cli의 출력이 바뀌면 워크벤치가 영향을 받는다. 같은 레포, 같은 버전, 같은 빌드에서 테스트가 잡는다.

## 위험

- **요소 → 소스 위치(M18)**: Thymeleaf에는 소스 맵이 없다. dev 미리보기 요청에서만 요소에 `템플릿:줄`을 싣는 처리기를 만들 계획이다. fragment가 여러 겹일 때 어느 줄을 가리킬지는 M18에서 정한다. 안 되면 fragment 단위(`th:fragment` 선언 위치)까지만 가리킨다.
- **Java가 바뀌면 다시 실행해야 한다**: 만든 화면이 바로 보이지 않는다. 계획 화면이 알린다.
- **미리보기 틀**: 런타임의 기본 헤더는 프레임 안에 넣는 것을 막는다. 워크벤치는 카탈로그가 미리보기를 넣는 방식을 그대로 쓴다. M17에서 확인한다.
- **스펙 YAML 저장(M21)**: SnakeYAML은 주석과 모양을 보존하지 않는다. 값만 바꾸는 줄 단위 편집으로 하고, 안 되는 모양이면 저장하지 않고 알린다.
- **레시피가 범위를 정한다**: 이미 있는 화면에 필드를 더하는 일은 보류한 `cozy add field`(ADR-0033)와 같은 문제다. 워크벤치도 하지 못한다.
- **작은 모델이 복사한 맥락을 잘 쓰는지**는 사용자의 내부 평가로 확인한다.
