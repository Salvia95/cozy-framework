# UI 디자인 기준

Cozy 화면을 만들 때 무엇을 목표로 하고, 어떤 순서로 판단하고, 무엇으로 끝났다고 볼지를 정한다. 이 문서만 읽고도 작업을 시작할 수 있어야 한다. 값과 마크업의 자세한 내용은 `references/`에 있고, 아래 "자세한 기준"에 적은 상황이 되면 그때 읽는다.

## 목적

Cozy 화면은 폐쇄망 Windows PC에서 업무 담당자가 날마다 쓰는 내부 도구다. 화려함보다 예측할 수 있는 화면이 중요하다. 디자인 작업의 목표는 세 가지다.

- **예측할 수 있다.** 같은 종류의 일은 어느 화면에서나 같은 자리에, 같은 모양으로, 같은 말로 나온다. 처음 여는 화면도 다른 화면에서 익힌 대로 쓸 수 있다.
- **누구나 읽을 수 있다.** 글자는 배경과 충분히 대비되고(WCAG 2.2 AA), 뜻을 색 하나로만 전하지 않으며, 한글은 단어 중간에서 줄이 바뀌지 않는다.
- **누가 만들어도 같은 화면이 나온다.** 사람이든 작은 LLM이든, 앱을 만드는 쪽은 원칙을 외우지 않고 컴포넌트를 조합한다. 원칙은 프레임워크의 패턴·컴포넌트와 빌드 검사 안에 들어 있다.

그래서 디자인 작업은 화면마다 새로 멋을 내는 일이 아니다. 정해진 체계 안에서 화면을 맞추고, 체계에 빈 곳이 있으면 체계를 고치는 일이다. 화면 하나의 취향보다 체계 전체의 일관성이 앞선다.

## 체계의 모양

| 층 | 무엇이 맡는가 | 가져오는 것 |
| --- | --- | --- |
| 구현 | Tabler (CSS, 마크업 구조, 12칸 그리드, 간격 단계) | 그대로 쓴다. Cozy는 대비가 모자라는 곳만 `cozy.css`에서 고친다 |
| 원칙 | Shopify Polaris | 색은 의미에만, 영역마다 주 버튼 하나, 피드백 종류 고르기 |
| 흐름 | AWS Cloudscape | 만들기·상세·수정·삭제 화면의 구성, 버튼 문구, 검증 시점, 삭제 확인, 빈 상태 구분 |

- Polaris와 Cloudscape에서는 원칙만 가져온다. 코드, 토큰 값, 문서 문장은 라이선스 때문에 가져오지 않는다.
- 템플릿은 layout → pattern → component → icon의 네 계층이다. 위 계층만 아래 계층을 쓴다. 앱 화면은 레이아웃에 패턴 하나를 넣고 컴포넌트로 채운다.
- 바꿀 수 없는 조건이 있다. CSP가 인라인 `<script>`와 `style=`을 막는다. 폐쇄망이므로 외부 URL을 쓰지 않는다(모든 자산을 앱이 서빙한다). `docs/adr/0017-version-policy.md`에 없는 의존성은 더하지 않는다.

## 행동 원칙

모든 디자인 작업에 적용한다. 판단이 막히면 이 원칙으로 돌아온다.

- **목적과 유형을 먼저 정하고 마크업은 마지막에 쓴다.** 사용자가 그 화면에서 끝내려는 일(찾기, 만들기, 확인하기, 고치기, 지우기, 훑어보기)을 한 문장으로 적는다. 목적이 화면 유형을 정하고, 유형이 패턴·폭·버튼 자리를 정한다. 목적을 한 문장으로 쓸 수 없으면 화면을 나눠야 한다는 신호다.
- **있는 것을 먼저 쓰고 새로 만드는 것은 마지막에 한다.** 같은 앱의 같은 유형 화면, 패턴 카탈로그(`/cozy/dev/catalog`)와 `cozy/fragments.yml`, Tabler의 마크업 구조를 이 순서로 찾는다. 맞는 것이 없을 때만 새 fragment를 만든다.
- **의미만 정하고 모양은 컴포넌트에 맡긴다.** 상태는 tone 이름으로 넘기고 색 클래스를 고르지 않는다. 위계는 크기와 굵기로 나눈다. 아이콘은 글자의 뜻을 거들 뿐 뜻을 혼자 전하지 않는다.
- **시선은 왼쪽 위에서 오른쪽 아래로 흐른다.** 제목은 왼쪽 위, 화면 전체의 동작은 오른쪽 위, 폼의 끝 동작은 오른쪽 아래다. 버튼 묶음마다 주 버튼은 하나이고 맨 오른쪽에 둔다. 되돌릴 수 없는 동작은 주 자리에 두지 않고 확인 창을 거친다.
- **모든 상태를 설계한다.** 데이터가 있을 때만 맞는 화면은 미완성이다. 기본, 아직 없음, 조건에 맞는 것 없음, 입력 오류, 처리 결과, 여러 페이지, 요청 중, 요청 실패를 각각 어떻게 보일지 정하고 화면 명세의 상태로 남긴다.
- **사용자의 말로 쓴다.** 버튼은 "대상 + 동사", 결과 알림은 "대상을 + 과거형", 오류는 무엇을 하면 되는지를 쓴다. 한 개념에는 한 용어를 쓰고, 통용되는 표현을 쓰며, 새 조어를 만들지 않는다.
- **눈대중이 아니라 측정으로 판단한다.** 대비, 폭, 정렬, 겹침은 DOM에서 잰 수치로 판단한다. 스크린샷은 근거를 보여 주는 자료이지 판단 기준이 아니다. 판단할 수 없는 것은 통과로 넘기지 않고 실패로 닫는다.
- **원칙이 맞지 않으면 화면보다 결정을 먼저 바꾼다.** 원칙이 다루지 않는 상황이나 원칙과 부딪히는 요구를 만나면 예외 화면을 만들지 않는다. 사용자에게 알리고 ADR 개정안을 제안한다. 검사를 통과시키려고 규칙을 완화하거나 검사를 건너뛰지 않는다.

## 작업 순서

1. **작업의 종류를 가린다.** 아래 "상황별 할 일" 표에서 해당하는 줄을 찾는다. 여러 줄에 걸치면 모두 따른다.
2. **목적, 화면 유형, 상태 목록을 먼저 적는다.** 마크업을 쓰기 전에 화면마다 "목적 한 문장, 유형(목록, 만들기, 상세, 수정, 개요, 목록+상세, 워크벤치 유형), 그릴 상태"를 적어 둔다.
3. **재사용할 패턴과 컴포넌트를 고른다.** 카탈로그와 매니페스트에서 찾고, reference-app의 같은 유형 화면을 기준 예시로 연다.
4. **마크업과 문구를 쓴다.** Tabler 구조를 따르고 색은 tone으로, 아이콘은 `cozy/icon/tabler`로, 문구는 문구 규칙대로 쓴다.
5. **상태를 명세에 남긴다.** 앱 화면은 `specs/{모듈}-{화면}.yml`에, 프레임워크 fragment는 `cozy/fragments.yml`의 `samples`에 상태를 적는다. 렌더링 검사와 카탈로그·워크벤치 미리보기가 이 상태를 쓴다.
6. **검사를 통과시킨다.** `cozy check`나 `mvn -o verify`로 빌드 규칙과 렌더링을 확인하고, 화면에 보이는 것이 바뀌었으면 `runtime-verifier` 서브 에이전트로 실제 화면을 확인한다.
7. **문서를 맞춘다.** 공개 API(패턴·컴포넌트 시그니처, 매니페스트 형식, 설정 속성)를 바꿨으면 `docs/conventions/`를 고친다. 원칙을 바꿔야 했다면 화면을 고치기 전에 ADR 개정안을 먼저 낸다.
8. **보고한다.** 바꾼 화면, 확인한 상태와 화면 너비, 측정 결과, 스크린샷, 남은 위험을 적는다.

## 상황별 할 일

| 상황 | 먼저 할 일 | 끝났다고 볼 기준 |
| --- | --- | --- |
| 앱에 새 화면을 만든다 | 생성 앱이면 `cozy add crud`나 `cozy add screen`으로 구조를 만들고 남은 칸만 채운다. reference-app처럼 손으로 쓰는 예시 앱이면 같은 유형의 기존 화면을 본떠 패턴을 고른다 | 화면 명세에 필요한 상태가 모두 있고, `mvn -o verify`와 화면 확인을 통과한다 |
| 앱 화면을 고친다 | 고치는 화면의 유형과 상태 목록을 다시 확인하고, 바꾼 뒤에도 그 유형의 배치와 폭이 유지되는지 본다 | 바꾸기 전의 모든 상태가 여전히 렌더링되고, 화면 확인을 통과한다 |
| 프레임워크 패턴이나 컴포넌트를 만들거나 바꾼다 | 정말 새 것이 필요한지 기존 조합으로 안 되는지 먼저 따진다. 시그니처를 바꾸면 그 fragment를 쓰는 모든 곳(reference-app, 아키타입 home, cozy 명령의 레시피 템플릿, 위반 픽스처)을 찾는다 | 매니페스트 항목과 샘플이 있고, 쓰는 곳이 모두 따라왔고, `docs/conventions/ui.md`가 맞고, 화면 확인을 통과한다 |
| `cozy.css`나 `cozy.js`, 디자인 토큰을 바꾼다 | 바꾸는 값이 원칙(tone, 대비, 폭, 글자 단계)을 바꾸는지 따진다. 바꾼다면 ADR 개정이 먼저다 | 영향받는 모든 화면 유형을 화면 확인으로 다시 재서 대비와 폭이 기준 안에 있다 |
| 워크벤치 화면을 만들거나 바꾼다 | 워크벤치 전용 화면 유형(전체 너비 3단, 높은 밀도)과 용어집을 따른다. 앱 화면 유형을 섞지 않는다 | 용어가 용어집과 같고, 이름이 데이터에서 오고, 화면 확인을 통과한다 |
| 화면 문구만 고친다 | 문구 규칙과 용어 원칙을 확인하고, 같은 개념이 다른 화면에서 어떤 말로 쓰이는지 찾는다 | 같은 개념이 앱 전체에서 같은 말이다 |
| 화면이나 결과를 검토한다 | 화면마다 유형을 먼저 판정하고, 그 유형의 기준으로 배치·폭·버튼·색·문구·상태를 본다 | 지적마다 어긋난 기준과 측정값이 붙어 있다 |
| 원칙이 다루지 않는 요구를 받는다 | 가장 가까운 화면 유형과 패턴으로 풀 수 있는지 본다. 안 되면 만들기 전에 사용자에게 알리고 ADR 개정안을 낸다 | 사용자가 결정했고, 결정이 ADR과 `design.md`에 들어갔다 |

## 판단이 갈릴 때

- **기준 문서의 순서**: ADR(`docs/adr/`)의 결정 → `docs/conventions/design.md`의 원칙 → `ui.md`·`rules.md`·`workbench.md`의 사용법과 검사 → 프레임워크 템플릿과 reference-app의 기준 예시 → Tabler 기본값. 앞의 것이 이긴다.
- **이 스킬과 문서가 다르면 문서가 맞다.** 이 스킬은 문서를 행동 순서로 다시 엮은 것이다. 다른 곳을 찾으면 문서대로 하고 이 스킬을 고친다.
- **예시와 원칙이 다르면 원칙이 맞다.** 기존 화면이 원칙을 어기고 있으면 따라 하지 말고 결함으로 보고한다.
- **두 원칙이 부딪히면 사용자의 판단이 필요하다.** 어느 쪽을 고를지 임의로 정하지 않는다. 두 안과 권장안을 적어 묻는다.

## 자세한 기준

필요한 상황이 되었을 때만 읽는다. 각 줄의 앞부분이 그 문서를 읽어야 하는 때다.

- 화면을 새로 만들거나 화면의 큰 틀을 바꾸면서 어떤 패턴을 쓰고 본문을 몇 칸으로 나눌지 정해야 할 때, 유형별 패턴·폭·칸 나누기·패턴 인자를 담은 [화면 유형과 배치](references/screen-types.md)를 읽는다.
- 버튼을 더하거나 옮기거나, 주 버튼과 보조 버튼, 삭제 버튼, 경로 표시의 자리를 정해야 할 때, 머리·폼·확인 창·표에서의 버튼 순서를 담은 [버튼과 동작 배치](references/actions.md)를 읽는다.
- 만들기·상세·수정·삭제 화면이나 그 컨트롤러를 만들거나 고칠 때, 주소, 리다이렉트, 검증 시점, 결과 알림 문구, 삭제 확인의 흐름을 담은 [만들기·상세·수정·삭제 흐름](references/crud-flow.md)을 읽는다.
- 빈 화면, 검색 결과 없음, 입력 오류, 처리 결과, 요청 중·실패 화면을 그리거나, 알림을 플래시·알림·토스트·확인 창 중 무엇으로 보일지 골라야 할 때, 상태 목록과 피드백 선택 기준을 담은 [상태와 피드백](references/states-and-feedback.md)을 읽는다.
- 색, tone, 배지, 글자 크기, 굵기, 간격, 밀도를 정하거나 대비 문제를 고칠 때, tone 표와 토큰, 허용 클래스, 글자 단계, 간격 단계를 담은 [색, 글자, 간격](references/color-type-spacing.md)을 읽는다.
- 버튼, 화면 제목, 알림, 빈 상태, 오류 문구를 쓰거나, 화면에 보일 용어와 표시 이름을 정할 때, 문구 규칙과 용어 원칙을 담은 [문구와 용어](references/copy-and-terms.md)를 읽는다.
- 화면 템플릿의 마크업을 직접 쓰거나 고칠 때, 화면 골격, 패턴에 영역 넘기기, htmx 부분 갱신, fragment 이름, 아이콘, CSP 제약, 템플릿 폴더 규칙을 담은 [마크업 작성](references/markup.md)을 읽는다.
- 어떤 컴포넌트가 있는지, 그 시그니처와 인자가 무엇인지, 비슷한 컴포넌트 중 무엇을 골라야 하는지 확인할 때, 패턴과 컴포넌트의 용도와 호출 예를 담은 [패턴과 컴포넌트 목록](references/components.md)을 읽는다.
- cozy-ui의 레이아웃·패턴·컴포넌트를 새로 만들거나 시그니처를 바꾸거나, `cozy.css`·`cozy.js`·벤더 자산을 바꿀 때, 매니페스트 항목 쓰는 법, 파급 범위, 문서화 대상을 담은 [프레임워크 UI 바꾸기](references/framework-ui.md)를 읽는다.
- 워크벤치(`/cozy/dev/workbench`) 화면을 만들거나 고칠 때, 3단 구성, 밀도, 용어집, 이름의 출처, 구조화된 입력 규칙을 담은 [워크벤치 화면](references/workbench.md)을 읽는다.
- 화면 작업을 마무리하면서 무엇을 검사하고, runtime-verifier에 무엇을 맡기고, 결과를 어떻게 판정하고 보고할지 정할 때, 빌드 검사와 화면 확인 항목, 위임 문안, 보고 형식을 담은 [검사와 화면 확인](references/verification.md)을 읽는다.

## 하지 않는 것

- 앱 템플릿에 색 클래스(`bg-*`, `text-red`, `btn-outline-danger` 등)를 직접 쓰지 않는다. 허용되는 것은 `text-secondary`, `text-muted`, `btn-primary`뿐이다.
- `style=`, `<style>`, `<script>`, `<link>`, `hx-on`, `onclick=`을 템플릿에 쓰지 않는다. 보정은 `cozy.css`에, 동작은 `cozy.js`에 둔다.
- 패턴 없이 `container-xl`, `page-header`, `page-body` 같은 화면 틀을 직접 만들지 않는다.
- 상세 화면에서 바로 고치게 하지 않는다. 수정은 별도 화면이다.
- 만들기·수정·삭제 결과를 토스트로 알리지 않는다. 플래시로 알린다.
- 입력하는 중에 검증 오류를 띄우지 않고, 주 버튼을 비활성화하지 않는다.
- 표 안에 주 버튼을 두지 않고, 한 버튼 묶음에 주 버튼을 둘 이상 두지 않는다.
- 분류를 색으로 나누지 않고, 숫자 카드와 활동 아이콘에 색을 입히지 않는다.
- 12px보다 작은 글자를 쓰지 않고, 한 화면 안에서 밀도를 섞지 않는다.
- 새 조어를 만들지 않고, 한 개념을 화면마다 다른 말로 부르지 않는다.
- 외부 URL, CDN, 외부 글꼴을 쓰지 않는다.
