# 워크벤치 화면

워크벤치(`/cozy/dev/workbench`, 모듈 `cozy-workbench`) 화면을 만들거나 고칠 때의 기준이다. 원문은 `docs/conventions/workbench.md`, `docs/conventions/design.md` §2의 "워크벤치 전용 유형", `docs/adr/0038-workbench-redesign.md`다.

## 워크벤치가 앱 화면과 다른 점

워크벤치는 개발자가 앱의 구조와 화면을 살피고 고치는 dev 전용 도구다. 업무 사용자가 쓰는 앱 화면과 목적이 다르므로 화면 유형도 따로 있다. 그래도 Tabler 구조, 색과 대비, 문구의 원칙은 같다.

| | 앱 화면 | 워크벤치 화면 |
| --- | --- | --- |
| 폭 | `container-xl` 또는 가운데 48rem | 전체 너비(`container-fluid`) |
| 구성 | 머리 + 본문 카드 | 머리 한 줄 + 칸마다 따로 스크롤하는 영역 |
| 밀도 | 보통 | 높음(목록과 표의 줄 간격이 좁다) |
| 글자와 대비 | 12px 이상, 4.5:1 | 같다 |
| 스크립트 | `cozy.js` | `cozy.js` + `/cozy/workbench.js` |
| CSS 클래스 | `cozy-*` | `cozy-workbench-*` |

- 워크벤치 유형을 앱 화면에 쓰지 않는다. 앱 화면 유형을 워크벤치에 섞지 않는다.

## 화면 유형

| 화면 | 폭 | 구성 |
| --- | --- | --- |
| 화면 보기 | 전체 너비 | 머리 한 줄(워드마크, 메뉴, 검색 칸) · 왼쪽 18rem(화면 목록, 구조 트리) + 가운데(미리보기나 소스) + 오른쪽 21rem(속성이나 샘플 데이터) |
| 개요 | 전체 너비 | 같은 머리 · 숫자 카드 줄 → 넓은 칸 7(화면 목록) + 옆 칸 5(규칙 위반, 모듈, 미구현 항목). 앱 `overview`와 같은 순서 |
| 검색 | 가운데 56rem | 같은 머리(검색 칸은 화면 안으로) · 검색 칸 → 묶음마다 카드 하나의 결과 목록 |

- 세 칸은 화면 높이를 채우고 칸마다 따로 스크롤한다. 1200px보다 좁으면 가운데, 왼쪽, 오른쪽 순서로 한 열에 쌓인다.
- 모든 워크벤치 화면은 같은 머리를 쓴다. 워드마크는 개요로 간다.
- 좌우 칸은 접을 수 있고 접은 상태는 브라우저(`localStorage`)에 남는다. 주소에는 넣지 않는다.
- 고른 것(화면, 상태, 화면 너비, 보기)은 주소의 파라미터에 둔다. 주소를 주고받으면 같은 화면이 보여야 한다.

## 정보를 보이는 방법

워크벤치 디자인 결함의 원인은 cozy 명령의 출력을 그대로 화면에 옮긴 것이었다. 식별자가 이름 자리에 나오고, 구조가 있는 정보가 글자 목록으로 나왔다. 그래서 정보의 모양에 맞는 표시를 고른다.

| 정보의 모양 | 표시 |
| --- | --- |
| 한 대상의 여러 속성 | 속성 표. 왼쪽 열이 항목 이름 |
| 같은 모양의 객체 목록 | 그리드(`cozy-workbench-grid`) |
| 포함 관계 | 트리. 안의 마디는 세로 선으로 잇고, 마디가 있는 줄은 접고 편다(`<details>`) |
| 모듈 사이 의존 | 계층형 다이어그램(서버가 계산한 SVG). 참조하는 쪽이 왼쪽, 실선은 의존, 점선은 이벤트. 많으면 표로 전환 |
| 많은 변경 파일 | 모듈과 계층(공개 API, 내부 구현, 화면, SQL, 화면 명세, 테스트, 설정)별 트리 |

- **값의 종류에 맞는 입력을 쓴다.** 읽기 전용 값은 글자, 직접 입력하는 값은 입력란, 정해진 값 중에서 고르는 값은 드롭다운이다. boolean은 체크박스나 드롭다운, 숫자·날짜·enum은 그 타입의 입력이다.
- **앱에 이미 있는 값은 고르게 한다.** 모듈, 엔티티, 이벤트, 인터페이스, DTO는 드롭다운이다. 예외: 새 모듈을 만들 수 있는 칸은 제안이 붙은 글자 칸이고, 아이콘(5,233개)은 이름 목록이 붙은 글자 칸이며 고른 아이콘을 칸 앞에 그린다.
- **반복 입력은 그리드, 단일 입력은 속성 표다.**
- **긴 결과는 묶는다.** 한 표에 수십 줄을 늘어놓지 않고 트리나 접는 묶음으로 나눈다. 개요의 화면 목록은 모듈마다 접고, 화면이 12개를 넘으면 위반이 있는 모듈만 펼친다.
- **한 번에 하나를 고르고, 비교는 따로 연다.** 미리보기의 상태는 하나만 고른다. 여러 상태 비교는 모달(최대 4개, 두 열, 창 크기 고정)에서 한다.

## 용어와 이름

- 워크벤치의 모든 낱말은 `docs/conventions/workbench.md`의 용어표를 따른다. 표에 없는 새 개념이 생기면 용어표에 먼저 넣는다. `WorkbenchTermsTest`가 메뉴, 상태 이름, 구조 트리, 생성 항목 목록을 확인한다.
- 사람이 읽는 이름이 앞, 식별자가 뒤(고정폭 회색)다: `목록 탐색 list-with-filter`.
- 이름은 데이터(매니페스트 `label`, 화면 명세 `title`, `cozy recipes --json`의 `title`·`group`, DTO Javadoc, `RuleNames`)에서 가져온다. 템플릿에 직접 적지 않는다. 출처 표는 `copy-and-terms.md`에 있다.
- 구조 트리의 이름 앞에 종류 배지를 두지 않는다. 종류는 속성 패널과 줄의 `title`에 둔다.
- 에이전트에게 넘기는 글("에이전트용 복사")은 식별자로 쓴다.
- cozy 명령이 낸 메시지(레시피 설명, 고치는 법, 다음 할 일)는 그대로 보인다.

## 고치는 기능의 범위

- 워크벤치는 cozy 명령을 거쳐서만 파일을 바꾼다. 워크벤치에만 있는 쓰기 로직을 만들지 않는다.
- 쓰기 전에 항상 "변경 파일 확인"(`--dry-run` 결과)을 보이고, "적용"으로 실행한다. 거절되면 이유를 보이고 파일은 그대로다.
- 고칠 수 있는 것: fragment 호출의 문자열 리터럴 인자(`cozy set arg`), 샘플 데이터의 값과 행(추가, 복제, 삭제), 상태 복제, 코드 생성.
- 고치지 않는 것: 자유 배치, 색·간격 편집, 템플릿 본문 편집, 스펙의 키 추가·삭제. 이 범위를 넓히려면 ADR 개정이 먼저다.
- 쓰는 요청은 CSRF, 같은 Origin, 프로젝트 폴더 조건을 지킨다.
- 미리보기는 빌드 결과의 템플릿을 그리므로 다시 빌드해야 바뀐다. 구조 트리와 속성은 소스를 읽어 바로 바뀐다. 화면이 이 차이를 알린다.

## 기준 예시와 확인

- 템플릿: `cozy-workbench/src/main/resources/templates/cozy/dev/workbench*.html`.
- 워크벤치 화면을 바꾸면 runtime-verifier로 개요, 화면 보기(세 칸, 칸 접기, 1200px 미만 쌓임), 상태 비교 창, 검색을 확인한다. 높은 밀도에서도 V9 대비 기준은 같다. 선택한 트리 항목의 글자 대비가 4.33:1로 미달했던 적이 있다.
