# 검사와 화면 확인

화면 작업을 마무리할 때 무엇을 검사하고, runtime-verifier에 무엇을 맡기고, 결과를 어떻게 판정하고 보고할지의 기준이다. 원문은 `docs/conventions/testing.md`, `docs/conventions/rules.md`, `.claude/agents/runtime-verifier.md`, `docs/conventions/design.md` §8이다.

## 왜 두 단계인가

빌드 검사는 HTML이 맞는지, 규칙을 지켰는지를 본다. 사이드바가 푸터를 가리는 것, 아이콘이 그려지지 않는 것, 카드에 여백이 없는 것, 대비가 모자라는 것은 실제 브라우저에서만 보인다. 그래서 빌드 검사를 통과한 뒤 실제 화면을 잰다. 둘 중 하나만으로는 끝났다고 보지 않는다.

## 1단계: 빌드 검사

```bash
source ~/.sdkman/bin/sdkman-init.sh
mvn -o verify                                     # 전체
mvn -o verify -pl samples/reference-app -am       # reference-app만
mvn -o package -pl cozy-cli && java -jar cozy-cli/target/cozy-cli-*.jar check --project samples/reference-app   # 빠른 규칙 검사
```

| 검사 | 무엇을 잡는가 |
| --- | --- |
| C2 템플릿 경계 (R1~R15) | 폴더와 참조 방향, 동적 참조, 매니페스트 누락, fragment 이름, 아이콘 이름(R13), 색 클래스와 tone(R14), 주 버튼 개수와 위치(R15) |
| C3 렌더링 | 화면 명세의 모든 상태와 매니페스트의 모든 샘플이 예외 없이 200으로 그려지는지, fixture가 DTO 타입과 맞는지 |
| C4 HTML | 렌더링 결과의 vnu 오류, 허용 목록에 없는 `hx-*` |
| C5 스펙 누락 | 화면 명세가 없는 화면, 매니페스트에 없는 spi fragment |
| C7 뷰 모듈 | 컨트롤러가 다른 모듈의 뷰를 반환 |

- 실패 메시지에는 규칙 ID, 위치, 고치는 법이 한 줄에 있다. `고치는 명령: cozy …`가 붙으면 그대로 실행한다.
- 아키타입을 바꿨으면 `mvn -o verify -pl cozy-archetype -am`, cozy 명령의 레시피 템플릿을 바꿨으면 `mvn -o verify -pl samples/recipes -am`도 돌린다(몇 분 걸린다).
- 검사를 통과시키려고 규칙을 완화하거나 테스트를 건너뛰지 않는다.

## 2단계: 화면 확인 (runtime-verifier)

화면에 보이는 것(cozy-ui 템플릿, `cozy.css`, `cozy.js`, 앱 템플릿, 워크벤치 화면)을 바꾸면 보고 전에 반드시 `runtime-verifier` 서브 에이전트로 확인한다. 이 에이전트는 실제 앱을 띄우고 agent-browser로 화면을 돌며 DOM을 잰다. 저장소는 바꾸지 않는다.

### 맡길 때 적을 것

runtime-verifier는 위임 문안만 보고 일한다. 아래를 빠짐없이 적는다.

- **대상 앱**: reference-app인지, 생성한 앱(경로와 메인 클래스)인지.
- **다시 설치할 모듈**: 바꾼 프레임워크 모듈(`cozy-ui`, `cozy-rules`, `cozy-test`, `cozy-workbench` 등).
- **사용자 경로**: 화면을 어떤 순서로 지나갈지. 예: 빈 목록 → 메모 만들기(빈 제목으로 저장 → 오류) → 저장 → 상세(플래시) → 수정(바꾸지 않고 저장 → 변경 없음) → 삭제 확인 → 목록(플래시).
- **상태**: 화면마다 확인할 상태(아직 없음, 조건 결과 없음, 입력 오류, 처리 결과, 여러 페이지 등).
- **화면 너비**: 기본 1280×800. 배치, 내비, 그리드를 바꿨으면 390×844도. 폭과 가운데 정렬은 1920에서 잰다.
- **바꾼 것과 특히 볼 곳**: 이번에 바꾼 요소와 그 요소에 해당하는 검사.

### 화면 확인 항목

| 확인 | 무엇을 재는가 |
| --- | --- |
| V1 화면 틀 | 사이드바와 `.page-wrapper`가 겹치지 않고, 푸터가 `.page-wrapper` 안 사이드바 오른쪽에 있다 |
| V2 머리와 본문 | 패턴 화면마다 `.page-header` 다음 `.page-body`, 제목과 동작이 한 줄 |
| V3 아이콘 | 모든 `svg.icon`의 크기가 0보다 크고 `<use>`가 그려진다 |
| V4 카드 여백 | 카드 안 내용이 테두리에 닿지 않는다 |
| V5 가로 넘침 | `scrollWidth - clientWidth`가 0 |
| V6 상태 | 빈 상태, 검증 오류, 성공 플래시, 데이터 있음이 설계대로 |
| V7 오류 | 페이지 오류, 콘솔 오류, 실패한 요청이 없다 |
| V8 부분 갱신 | htmx 응답이 대상만 바꾼다(검증 오류 응답에 `<form>`이 하나) |
| V9 대비 | 보이는 모든 글자 4.5:1(큰 글자 3:1), 아이콘과 포커스·경계선 3:1 |
| V10 동작 | 영역마다 주 버튼 하나, 맨 오른쪽. 폼 동작은 오른쪽 아래, 삭제는 확인 창 |
| V11 폭과 정렬 | 목록·상세·개요는 `container-xl`이고 가운데(1920에서 좌우 차 ±2px), 폼은 가운데 48rem 이하, 제목 왼쪽 끝 = 첫 카드 왼쪽 끝 |

### 결과 판정

- 판정은 PASS, FAIL, UNSURE다. UNSURE는 DOM으로 판단할 수 없는 것에만 쓰고, 통과로 반올림하지 않는다.
- FAIL마다 요소, 측정값, 고칠 템플릿이나 CSS의 위치가 붙어 있어야 한다. 없으면 다시 맡긴다.
- 요청하지 않은 결함(SIDE-FINDING)도 보고에 옮긴다.
- 스크린샷 도구가 입력에 남기는 `style=""` 때문에 CSP `style-src-attr` 위반이 생길 수 있다. 스크린샷 없이 다시 재현될 때만 결함으로 본다.
- FAIL을 고친 뒤에는 그 항목을 다시 확인받는다.

## 보고

- 첫 문장: 어떤 화면이 통과했고 어떤 화면이 실패했는지.
- 바꾼 것: 화면, 컴포넌트, CSS·JS, 문서.
- 통과한 검사: 빌드 검사 명령과 결과, 화면 확인 표(화면 × 상태 × 너비 × 확인 항목).
- 스크린샷: 화면, 상태, 너비가 드러나는 파일 이름(`NN-<화면>-<상태>-<너비>.png`).
- 남은 위험: 확인하지 못한 경로와 이유, 원칙이 다루지 않아 판단을 미룬 것, ADR 개정이 필요해 보이는 것.
- Windows에서만 확인할 수 있는 것(트레이, app-image 등)은 사용자 확인 항목으로 따로 적는다.
