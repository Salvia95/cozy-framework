# 상태와 피드백

빈 화면, 검색 결과 없음, 입력 오류, 처리 결과, 요청 중·실패를 그리거나, 알림을 어떤 방식으로 보일지 고를 때의 기준이다. 원문은 `docs/conventions/design.md` §3, §7과 `docs/conventions/ui.md`의 `cozy.js` 항목이다.

## 화면마다 확인할 상태

화면을 만들면 아래 상태를 하나씩 따져 보고, 해당하는 것은 화면 명세의 상태로 남긴다. 해당하지 않으면 왜 해당하지 않는지 말할 수 있어야 한다.

| 상태 | 언제 생기는가 | 무엇을 보이는가 |
| --- | --- | --- |
| 기본 | 값이 보통만큼 있다 | 설계한 화면 그대로 |
| 아직 없음 | 처음 쓰는 사용자, 만든 것이 하나도 없다 | 무엇이 없는지 + 다음에 할 일 + 만들기 버튼 |
| 조건에 맞는 것 없음 | 검색어나 필터 때문에 결과가 0건이다 | 조건을 바꿔 보라는 안내 + 조건 지우기 버튼 |
| 여러 페이지 | 한 페이지보다 많다 | 전체 건수, 이전·다음, 번호 5개 |
| 입력 오류 | 제출한 값이 검증에 걸렸다 | 칸 바로 아래 오류, 첫 오류 칸으로 포커스 |
| 처리 결과 | 만들기·수정·삭제가 끝나 다른 화면으로 왔다 | 그 화면 page-body 맨 위의 플래시 |
| 요청 중 | htmx 요청이 진행 중이다 | 화면 맨 위 진행 막대, 검색 칸 오른쪽 스피너 |
| 요청 실패 | 4xx·5xx 응답이나 연결 실패 | 토스트(critical) |
| 값이 비어 있는 칸 | 선택 항목이 비었다 | 기준 예시처럼 빈칸 대신 `text-secondary` 문장이나 "—" |

## 아직 없음과 조건에 맞는 것 없음을 구분한다

두 상태는 사용자가 다음에 할 일이 다르다. 하나로 합치지 않는다.

| 구분 | 판단 | 컴포넌트 | 버튼 |
| --- | --- | --- | --- |
| 아직 없음 | 조건 없이 조회했는데 0건 | `emptyStateAction(아이콘, '메모가 없습니다', '첫 메모를 만들어 보세요.', ~{::#empty-action})` | [메모 만들기] (주 버튼) |
| 조건에 맞는 것 없음 | 조건이 하나라도 있는데 0건 | `noResults('/memo')` | [조건 지우기] (조건 없는 목록 주소) |
| 만들 수 없는 곳의 빈 상태 | 사용자가 만들 수 없는 목록(활동 기록 등) | `emptyState(아이콘, 제목, 설명)` | 없음 |

- 판단은 템플릿에서 필터 값으로 한다(`th:if="${!#strings.isEmpty(filter.q) or filter.pinned}"`). 기준 예시는 reference-app의 `memo/api/list.html`이다.
- 빈 상태 문장은 "무엇이 없는지 + 다음에 할 일"이다: "메모가 없습니다. 첫 메모를 만들어 보세요."

## 피드백 종류 고르기

알려야 할 것이 생기면 아래 순서로 묻는다.

1. 사용자가 방금 한 만들기·수정·삭제의 결과인가 → **플래시**.
2. 특정 입력 칸의 문제인가 → **칸 오류**.
3. 화면에 머물러야 하는 안내나, 칸과 상관없는 오류인가 → **알림**.
4. 되돌릴 수 없는 동작을 하기 직전인가 → **확인 창**.
5. 사소한 확인(복사함)이거나 요청 실패인가 → **토스트**.
6. 기다려야 하는가 → **진행 표시**.

| 종류 | 자리 | 컴포넌트 | 사라지는가 |
| --- | --- | --- | --- |
| 플래시 | 이동한 화면 page-body 맨 위 | 컨트롤러 `CozyFlash.success/info/warning/critical`, 패턴의 `flash()`가 그린다 | 다음 화면에는 없다 |
| 칸 오류 | 칸 바로 아래 | `field`가 `th:errors`로 그린다 | 다시 제출할 때까지 |
| 알림 | 그 내용 바로 위(폼 오류는 버튼 위) | `alert(tone, 문장)` | 화면에 머문다 |
| 확인 창 | 화면 가운데 모달 | `deleteConfirm`, 일반 확인은 `modal` | 사용자가 닫는다 |
| 토스트 | 화면 구석 | 서버는 `HX-Trigger: {"cozy:toast": {"message": "…", "kind": "success"}}`, 스크립트는 `Cozy.toast(message, kind)` | 잠시 뒤 사라진다 |
| 진행 표시 | 화면 맨 위 막대, 검색 칸 오른쪽 | 막대는 자동, 스피너는 `loading()` | 요청이 끝나면 |

- **만들기·수정·삭제의 결과를 토스트로 알리지 않는다.** 토스트는 사라지므로 놓치기 쉽고, 리다이렉트 흐름과 맞지 않는다.
- 토스트는 중립 어두운 바탕이고 critical만 빨강이다. 성공 토스트를 초록으로 칠하지 않는다.
- 알림에는 종류별 아이콘이 붙는다. 색만으로 뜻을 전하지 않는다.
- 패턴을 쓰지 않는 화면(드물다)은 `cozy/component/alert :: flash()`를 page-body 맨 위에 직접 둔다.

## 요청 실패와 오류 화면

- htmx 요청의 4xx·5xx 응답과 연결 실패는 `cozy.js`가 토스트로 알린다. 화면이 따로 처리하지 않는다.
- 보통 요청의 오류 화면은 `templates/error/4xx.html`, `5xx.html`이다. 앱이 같은 경로에 두면 앱 것이 쓰인다.

## 상태를 남기는 곳

- 앱 화면: `specs/{모듈}-{화면}.yml`의 `states`. `default`와 `empty`는 필수이고, 입력 오류는 `_errors`로 만든다.
- 상태 이름은 관례 이름을 쓴다. 워크벤치가 한글 이름으로 보인다: `default` 기본, `empty` 데이터 없음, `noResults` 검색 결과 없음, `paged` 여러 페이지, `invalid` 입력 오류. 그 밖의 이름은 식별자 그대로 보인다.
- 프레임워크 fragment: `cozy/fragments.yml`의 `samples`.
- 렌더링 검사(C3, C4)가 모든 상태를 그리고 HTML을 검증한다. runtime-verifier의 V6가 실제 화면에서 상태마다 `.empty`, `.invalid-feedback`, `.alert`, 행이 있는지 본다.
